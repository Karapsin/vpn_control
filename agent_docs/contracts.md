# Product Contracts

This file is the single authoritative source for VPN Control product, platform, UI, state, protocol, localization, artifact, and release invariants. Focused documents describe owners, implementation procedures, troubleshooting, and test commands; they must cite these IDs instead of redefining requirements.

Contract IDs are stable. Update an existing contract when behavior changes, add a new ID for a new invariant, and update affected tests and focused docs in the same change. If another agent document conflicts with this file, this file wins for product behavior while root `AGENTS.md` wins for agent workflow and safety.

## Product And Data Contracts

- **PRODUCT-001 — Empty initial data.** A fresh install has no default subscriptions, routing rules, locations, or demo data.
- **PRODUCT-002 — Cross-platform parity.** Subscription parsing, source selection (including `All`), refresh results, location matching, Find Best candidate selection, secure DNS behavior, SSH Routing truth tables, update states, and user-visible statuses stay aligned across Android and desktop and between GUI and CLI unless a platform contract explicitly diverges. Parity covers reachable product actions and outcomes, not dormant methods or presentation gestures.
- **PRODUCT-003 — Additive compatibility.** New protocol or subscription formats do not break supported direct-link, line-based, base64, JSON, Clash, or persisted payloads. Existing serialized names require an explicit migration before they change. Saved state that a build cannot read, including state written by a newer build, is never overwritten or deleted: desktop keeps an unreadable `workspace.json` or recovery file in its private folder under a new name before it loads an older readable copy or the defaults, and reports the persistence failure in the GUI status and as a `status` warning; a first run without saved state starts from defaults without a warning. Desktop `workspace.json` records `format` 1: a workspace with any other `format` counts as unreadable, and a change that older builds would misread raises `format`.
- **PRODUCT-004 — Import/export round trip.** Direct link, clipboard, QR, and file paths preserve a supported configuration's meaning. Custom configurations remain full runtime JSON except for the narrowly allowed runtime transformations in `CONFIG-003`.
- **PRODUCT-005 — Safe updates.** Update checking, downloading, and checksum verification do not stop an active connection. Installation uses platform confirmation/elevation, may briefly disconnect, and preserves the prior reconnect/off intent.
- **PRODUCT-006 — Private data.** Diagnostics and reports do not expose subscription URLs, endpoints, UUIDs, credentials, tokens, or SSH private keys. Private keys never enter `PersistedState`, DataStore, `workspace.json`, generated documentation, or exported diagnostics.
- **PRODUCT-007 — Desktop default mode.** A new desktop workspace starts in VPN mode; macOS capability handling may direct the user to proxy-only without changing the persisted cross-desktop default.

## UI Contracts

- **UI-001 — Fixed appearance.** Android and desktop always use `VpnControlTheme`; light mode, system-derived dynamic colors, and independent platform palettes are unsupported.
- **UI-002 — Palette.** The application background gradient is `#08111F -> #12304B -> #16496B`; base/elevated surfaces are `#141F2D` and `#1D2B3B`; primary/accent are `#4B7BE5` and `#9ED6FF`; primary/secondary/muted text are `#FFFFFF`, `#D3E3EE`, and `#94A9B8`. Dialogs paint the base surface and dropdown menus the elevated surface. `VpnControlTheme` defines every Material color role from this palette, so no component shows a Material default color.
- **UI-003 — Semantic hues.** Green is used only for success/active state, amber only for warning/pending state, and red only for error/destructive state. Decorative backgrounds, navigation, ordinary actions, and selection use navy/azure.
- **UI-004 — Shape scale.** Small, medium, and large component shapes use 12, 18, and 24 dp corner radii. Pill controls may use a full radius when their shape conveys selection or state.
- **UI-005 — Accessibility geometry.** Visible content stays within its viewport and remains scroll-reachable. Interactive elements do not overlap, expose a non-empty accessible label, and provide at least a 48 by 48 dp target unless a documented native-control exception applies. A selectable composite row may contain separately actionable 48 dp child controls only when the geometry evidence explicitly names those containment pairs and child hit targets take precedence.
- **UI-006 — Complete surface coverage.** Every tab, submenu, dialog, menu state, enabled/disabled state, progress/error state, and supported OS-owned surface is represented in `visual-tests/scenes.json`. Adding or removing a visible element updates the scene's required-element inventory and its baseline in the same change.
- **UI-007 — Deterministic visual fixtures.** Visual fixtures use synthetic public data, frozen clocks/progress, canonical English, and fixed viewports. They never read the user's workspace or interact with an active VPN/runtime.
- **UI-008 — Localization stress.** The visual suite includes narrow/landscape, 1.3 Android font scale, 960x720 desktop at 125%, long German text, and Arabic RTL stress scenes. Catalog validation still covers every supported language.

## State And Action Ownership Contracts

- **STATE-001 — Shared purity.** Shared model/core owns cross-platform models, validation, draft mutation, selection decisions, state projection, status keys, parsing, refresh, and config-independent logic. Shared code does not directly perform Android APIs, desktop process control, filesystem IO, or OS permission work.
- **STATE-002 — Android side effects.** Android owns Android permissions and activity results, VPN service calls, WorkManager, installed-app catalogs, Android persistence, Android credential storage, and Android update/installer orchestration. Platform services execute effects returned from shared decisions instead of growing the ViewModel.
- **STATE-003 — Desktop side effects.** Desktop owns workspace files, runtime processes, TUN/privilege setup, tray/single-instance behavior, autostart, native dialogs, desktop credentials, direct-probe executables, diagnostics export, and desktop update/installer orchestration. `DesktopAppService` remains a facade/coordinator and delegates focused behavior.
- **STATE-004 — Shared-first decisions.** A decision used on more than one platform is extracted to shared core before platform call sites duplicate it. A genuine divergence is recorded in this file.
- **STATE-005 — Live-setting changes.** Saving runtime-affecting DNS, SSH, routing, mode, or related settings and manually selecting a location never replaces or stops a live connection. Both interfaces distinguish the committed next configuration from the actual active configuration and show pending restart until they match or the connection stops. Reverting to the active configuration clears pending state. Explicit restart applies committed settings, never an open GUI draft; `on` is idempotent while connected. Find Best remains an explicit selection-and-connect workflow with verification and rollback, not a deferred manual selection.

## Platform Contracts

- **PLATFORM-001 — Android.** Android provides the shared Compose UI, VPN mode through Android VPN APIs, supported proxy-only flows, app-package routing, in-app diagnostics export, and a direct-install APK. VPN permission is user-granted.
- **PLATFORM-002 — Linux desktop.** Linux provides Compose Desktop proxy-only and VPN modes. VPN requires `/dev/net/tun` and `CAP_NET_ADMIN` on the installed `sing-box`. Packages include DEB and RPM plus the Arch install/update paths.
- **PLATFORM-003 — Windows desktop.** Windows provides Compose Desktop proxy-only and VPN modes. VPN requires Administrator/Wintun; proxy-only remains usable without elevation. Packages include EXE and MSI. Windows path pins never stop other programs from creating, renaming or linking entries into the pinned folders: folder pins deny only the rename and deletion of the pinned folders, and only files whose content must stay immutable deny writers.
- **PLATFORM-004 — macOS desktop.** macOS provides Compose Desktop proxy-only mode and DMG packaging. Full VPN mode is not advertised or tested as supported until a privileged helper exists.
- **PLATFORM-005 — Desktop app assignment.** Android package assignment rules are not shown as functional desktop routing controls until equivalent OS-specific implementations exist.
- **PLATFORM-006 — Linux tray fallback.** The app auto-detects native AppIndicator/StatusNotifier/GtkStatusIcon support and can use AWT/XEmbed. i3/polybar-style XEmbed sessions prefer AWT; `VPN_CONTROL_LINUX_TRAY_BACKEND=native|awt` remains available for diagnosis. The window stays accessible until a tray icon is confirmed.
- **PLATFORM-007 — Platform update package.** Linux selects DEB, RPM, or Arch bundle from the installed family; Windows uses its installer flow; macOS uses its DMG flow; Android uses the package installer. Stable Android updates use the configured signer identity.

## Desktop Lifecycle Contracts

- **DESKTOP-001 — Single instance.** One background controller owns each resolved workspace, runtime, persistence, operations, and reconnect intent. GUI and CLI are clients of that owner. A second GUI launch activates the existing frontend; GUI attach, detach, or crash does not interrupt the controller's connection. Controller and frontend registration are distinct. A crashed or exited GUI's presentation lease is released as soon as its captured process is proven gone, so the next launch attaches immediately; uncertainty never releases a live GUI's lease.
- **DESKTOP-002 — Close to tray.** Closing hides the window only after a tray icon is confirmed available. Without a usable tray, the window remains accessible or the app exits instead of becoming invisible. On Windows an icon AWT accepted is no confirmation: the tray is usable only while the GUI's own desktop has a notification area (`Shell_TrayWnd`), a close or `gui hide` asks for it again, a window hidden in a tray whose notification area went away is shown, and a notification area that is not there yet (Explorer after an autostarted GUI) is waited for without limit, never taken for no tray.
- **DESKTOP-003 — Autostart visibility.** `--autostart` starts hidden only after tray availability; otherwise the window stays visible. Linux uses the XDG entry and maintains an i3-compatible marked fallback block when enabled from i3.
- **DESKTOP-004 — Reconnect intent.** GUI or persistent-service startup restores remembered reconnect intent once; ordinary CLI queries and transient controller startup never implicitly connect. Explicit off clears reconnect intent; graceful owner shutdown preserves the previous on/off intent.
- **DESKTOP-005 — Refresh continuity.** Scheduled subscription refresh belongs to the controller and continues without a GUI. It does not leave VPN/proxy stopped. A short controlled restart is allowed only when a generated config change requires it, preserving the actual active selection rather than prematurely applying a pending manual selection.
- **DESKTOP-006 — Direct probes.** Desktop Find Best and validation probes use the dedicated direct executable/routing so active VPN/proxy state cannot bias results. Custom profiles are excluded from Find Best candidates.
- **DESKTOP-007 — Scoped elevation.** Windows elevation is requested only for operations that need it; proxy-only remains available without Administrator privileges.
- **DESKTOP-008 — Headless command.** The supported persistent no-GUI entry point is `vpn-control serve` on Linux/macOS and `vpn-control-cli.exe serve` on Windows; the internal transient headless-controller argument is not a service interface. The persistent owner remains alive while disconnected. A second serve reports an existing owner without pretending to supervise it. Queries, help, and version do not initialize a GUI, tray, or display dependency.

## CLI Contracts

- **CLI-001 — Complete operation parity.** Every reachable GUI product operation has a terminal equivalent on each supported platform: connection control, source selection, subscriptions, locations, current routing, settings, SSH key import, session statistics, logs, diagnostics, operations, and updates. Files, stdin/stdout, and QR images replace native picker, clipboard, share, and camera gestures. Dormant advanced rule sets, bypass-app lists, statistics-visibility setters, and HWID setters are not restored as new public writes. Android is controlled through authenticated ADB on a non-debuggable installation without root.
- **CLI-002 — Same decisions and effects.** GUI and CLI invoke shared validated domain actions, preserving parsing, normalization, read-only subscription locations, import/export meaning, source eligibility, visible location ordering, Find Best verification/rollback, and durable persistence. Neither interface uses demo mutations or reports success from a status string. Platform capability differences are explicit; unsupported operations fail without changing configuration or silently substituting a mode.
- **CLI-003 — Authoritative state and operations.** One session owns committed configuration, active runtime identity, and operation state. GUI drafts and navigation remain local. Configuration revisions change only after committed changes; stale revision saves conflict without overwriting another client. Controller identity distinguishes revision epochs. Conflicting mutations serialize or return busy while reads and cancellation remain responsive. Requests have deduplication identities; a disconnected client queries a known operation rather than blindly replaying it against a new owner.
- **CLI-004 — Stable command protocol.** A shared typed registry owns operation IDs, grammar, aliases, argument metadata, capabilities, mutability, asynchronous support, GUI bindings or explicit presentation/service classification, contract references, and coverage IDs. JSON responses use a versioned envelope with controller/request/operation identity, result code, completion state, configuration revision, pending restart, data, and warnings. Watch/follow uses NDJSON. Exit codes are 0 for success or accepted async work, 1 for action/validation failure, 2 for unavailable/incompatible transport, timeout, or unknown outcome, and 130 for cancellation. Unknown options fail before GUI/controller startup. Raw stdout exports cannot be combined with JSON envelopes.
- **CLI-005 — Truthful completion.** Synchronous commands await durable persistence and required effects; asynchronous acceptance is not completion. Long operations expose progress, terminal results, and meaningful cancellation. This includes owner-run GUI and scheduled refresh work, not only CLI-originated requests. A client wait timeout does not cancel the underlying operation. Partial refresh, persistence failure, rollback failure, required OS interaction, and installer handoff are represented explicitly. Installer-started is not installed. Operation retention is bounded, and private input is not retained as operation metadata.
- **CLI-006 — Private authenticated local control.** Desktop control is authenticated over loopback with a fresh high-entropy per-owner credential in an owner-private endpoint descriptor and bounded versioned frames. Android checks Binder caller identity in addition to its protected provider permission on every call and stream. Authentication precedes side effects. Clients transfer content, not arbitrary server filesystem paths; private keys are input-only. Default summaries, logs, errors, and diagnostics are redacted. Explicit configuration inspection/export preserves usable configuration as in the GUI, except private keys. Secrets never appear in command arguments, request logs, or exception output.
- **CLI-007 — Safe interaction and lifecycle.** CLI writes obey STATE-005; pending selection/settings never replace a live session implicitly. Native permission, VPN consent, elevation, and installer confirmation remain mandatory. Android requires explicit interactive opt-in before launching required OS interaction. Windows standard-user queries, configuration, and proxy-only operation do not elevate the entire application. Presentation/service commands are desktop-only, not simulated Android daemons. Alternate state directories isolate all owner, lock, runtime, and update state; they do not make real TUN, autostart, or installer tests safe on the user's host.
- **CLI-008 — Packaged platform evidence.** Native Linux, Windows, macOS, and Android tests exercise the public CLI path, stdout/stderr and exit codes, Unicode/space-containing paths, configuration parity, operation progress/cancellation, and supported connection behavior. Desktop tests prove headless operation and GUI attach/detach with uninterrupted traffic and one runtime owner. Android tests cover authorized ADB, unauthorized callers, consent denial/grant, and process lifecycle on a non-debuggable build. Unit/contract tests precede fixes for integration-discovered product defects. Platform limitations are tested as explicit unsupported results rather than omitted commands or false success.

## sing-box And Networking Contracts

- **CONFIG-001 — Supported profiles.** Structured profiles support VLESS, Trojan, Shadowsocks, VMess, and SOCKS. `CUSTOM` stores a complete runtime JSON configuration.
- **CONFIG-002 — Shared config builders.** Non-custom outbound/TLS/transport generation and common DNS/route/rule-set generation are shared. Platform factories own inbounds, Android app assignments, desktop direct-probe rules, and runtime wrappers.
- **CONFIG-003 — Custom transform boundary.** Custom JSON may be transformed only for the loopback management proxy, isolated desktop direct probes, and optional SSH Routing. SSH transforms fail closed on unknown outbound/DNS types, unsupported top-level network features, invalid detour graphs, or reserved-tag collisions.
- **CONFIG-004 — SSH chain.** When enabled, application traffic follows `selected proxy -> remote loopback SOCKS relay -> pinned SSH outbound -> public network`; the SSH leg uses UDP-over-TCP v2. SSH host/bootstrap establishment is the intentional direct exception.
- **CONFIG-005 — SSH direct actions.** `DIRECT` rules, direct-domain suffixes, and remote rule-set downloads use SSH egress while SSH Routing is enabled. Active runtimes expose a loopback-only mixed management inbound for subscription downloads.
- **CONFIG-006 — Secure DNS modes.** `AUTOMATIC` uses `https://1.1.1.1/dns-query`; custom DoH accepts `https://` and supplies `/dns-query` when absent; custom DoT accepts `tls://` and defaults to port 853. Plain UDP/TCP custom DNS is rejected.
- **CONFIG-007 — Secure DNS wiring.** `secure-dns` is final, returns IPv4 answers, and detours through `proxy`. A direct `bootstrap-dns` at `1.1.1.1:53` resolves only proxy/encrypted-DNS establishment hosts. Only the bootstrap address enters direct CIDRs.
- **CONFIG-008 — DNS validation and migration.** Secure endpoints reject credentials, query strings, fragments, invalid ports, wrong schemes, and DoT paths. Legacy enabled raw-IP DNS migrates to automatic secure DNS while retaining the old value only for the migration notice.
- **CONFIG-009 — Routing defaults.** No default rules are added. With `ignoreRules=true`, all eligible traffic uses VPN. With `ignoreRules=false` and no Android app assignments, all apps use VPN. Configured direct-domain suffixes bypass VPN/proxy.
- **CONFIG-010 — Direct probe rule placement.** Desktop VPN config injects direct-probe process rules only in VPN mode and before DNS hijack rules.
- **CONFIG-011 — Find Best parity.** Android and desktop evaluate supported subscription candidates with shared selection logic where possible; results do not depend on whether VPN is currently active.
- **CONFIG-012 — Loopback-only listeners.** Generated sing-box inbounds listen on `127.0.0.1` on every platform. Every socket the desktop app itself listens on binds the loopback: free-port probes and port checks bind `127.0.0.1` through `DesktopLoopback`, and the control endpoint binds the JVM loopback address. A wildcard listen, even a momentary port probe, makes Windows Defender Firewall ask to allow network access; that prompt is a defect, not a step to approve. Inbounds written in a custom configuration keep the address their author gave.

## Localization Contracts

- **L10N-001 — Catalog ownership.** User-facing labels live in `i18n/*.json`; status, log, benchmark, and freeform runtime translations live in `i18n-status/*.json`. Kotlin does not contain translated `when (AppLanguage...)` branches.
- **L10N-002 — Generated language model.** `languages.json` owns supported languages; `AppLanguage` and lookup tables are generated. UI choices sort by visible display name with System pinned first.
- **L10N-003 — Typed statuses.** Stable runtime events use domain status facades and structured keys. UI/platform code does not concatenate encoded statuses into untranslated compound sentences.
- **L10N-004 — Catalog parity.** Every language has the English key/section shape and preserves all placeholders exactly. Technical commands, paths, URLs, capability names, and protocol identifiers stay recognizable.
- **L10N-005 — Legacy paths.** `dynamic` handles known parameterized legacy patterns, `legacyExact` handles persisted complete messages, and replacement lists are limited to stable fragments. Only `target` text is translated; `source` stays canonical.

## Artifact Contracts

- **ARTIFACT-001 — Tracked runtime inputs.** The Android AAR, Android ARM64 release runtime, Android x86_64 debug runtime, and the four desktop test fixtures named in `native-runtime-artifacts.md` are the only tracked native runtime inputs.
- **ARTIFACT-002 — Generated runtime outputs.** Desktop bundled runtime directories, all `build/`, `dist/`, `.runtime/`, downloaded packages, and prepared `sing-box` binaries remain untracked.
- **ARTIFACT-003 — Runtime provenance.** A tracked runtime refresh records upstream version and checksum, preserves architecture compatibility, and is not mixed with unrelated UI/localization work.
- **ARTIFACT-004 — Visual baselines.** Canonical PNG visual baselines under `visual-tests/baselines/<platform>/` are Git LFS objects. Actual screenshots, diffs, reports, machine fingerprints, and contact sheets are generated artifacts and remain untracked.

## Visual Regression Contracts

- **VISUAL-001 — Supported-platform gate.** A release requires complete automated results and agent screenshot verdicts for every Android, Linux, Windows, and macOS scene at the exact release SHA. A missing capture, result, verdict, receipt, or attestation blocks release.
- **VISUAL-002 — Capture boundary.** App-owned UI uses deterministic Compose/semantics capture; Android and desktop OS-owned consent, picker, chooser, tray/menu-bar, elevation, installer, notification, window-frame, DMG, and Gatekeeper surfaces use platform automation, full-screen except on Windows. A Windows OS-owned scene image is the target surface's own region, located by native handle or owning process: a window's DWM extended frame bounds or a notification icon's rectangle, canonically placed, unoccluded, and stable over two consecutive identical captures; several surfaces are stacked in a fixed layout. The full screen of the same moment is kept beside it as diagnostic evidence, bound in the capture provenance with the target identity, rectangle, placement, and stable-frame attempts, and is never compared. Arbitrary third-party target content after a chooser is excluded.
- **VISUAL-003 — Canonical environments.** Android uses Pixel 6/API 35 portrait; desktop uses 1280x800 at 100%. The agent prefers an isolated local emulator, native session, or VM, bootstraps and starts it when absent, and may dispatch a pinned GitHub-hosted ephemeral fallback only for capabilities that environment can faithfully expose. Windows UAC and macOS secure surfaces require a real local client VM/session.
- **VISUAL-004 — Comparison.** Only the scene image is compared, never a region capture's diagnostic frame. Dimensions match exactly. Per-channel deltas up to 8 are ignored; changed pixels above that threshold are at most 0.02%; mean absolute channel error is at most 0.25. Dynamic values inside the scene image are frozen, and no masks are allowed inside it.
- **VISUAL-005 — Geometry and contrast.** Every app-owned scene emits viewport, stable-element geometry, and measured text contrast. The gate rejects clipping, off-viewport bounds, overlapping interactive controls, undersized targets, missing labels/elements, and contrast below 4.5:1 for normal text or 3:1 for large text.
- **VISUAL-006 — Evidence.** Every capture subset binds its checked-out SHA, scene-file hashes, manifest, provider, and environment fingerprint. Every run preserves those records plus actual screenshots, baseline/actual/diff contact sheets, per-scene diffs, geometry data, comparison summaries, and scene-level agent verdicts. A release receipt hashes all evidence, the manifest, the environment contract, and the exact SHA.
- **VISUAL-007 — Baseline and failure handling.** Release verification is read-only. A product defect blocks; an infrastructure failure is retried or moved to an eligible provider; an intentional visual change updates reviewed Git LFS baselines on `dev`. Automation failures cannot be waived for the same SHA and require a new validated SHA after a fix or test/baseline correction.
- **VISUAL-008 — Agent-owned execution.** Persistent self-hosted visual runners and externally enrolled runner services are unsupported. The coding agent plans providers, boots only isolated environments it owns, captures or dispatches capability-compatible fallback scenes, combines the evidence, runs comparison, opens every screenshot/contact sheet, records every verdict, and stops only environments it started. Hosted capture never compares or attests independently.
- **VISUAL-009 — Exact-SHA attestation.** A full release review writes an ignored local receipt and posts the `vpn-control/agent-visual` commit status containing its digest. Targeted or partial reviews never create release approval. No human approval substitutes for the agent review.

## Validation Contracts

- **TEST-001 — Fast regression for every discovered failure type.** Every distinct product failure discovered in a VM, Android emulator, native or packaged-platform check, manual scenario, visual review, or integration job requires an implemented quick deterministic regression before integration, push, or completion. Preserve original failure evidence and relevant unfixed source/file beforeimages before editing. Within explicit file and environment ownership, workers may implement and test reversible quick fixes without coordinator micro-approval before constructing the regression; scope, runtime-interruption authorization, unknown-outcome non-replay, and source/artifact provenance gates remain binding. After the flow works, report the finite list of encountered failure types, known or unresolved causes, and proposed regression coverage. Proposals alone do not satisfy this contract. The same causal regression must actually fail on the preserved unfixed implementation (RED), then pass with the fix (GREEN); use an isolated owned copy for later RED rather than reverting shared or live native state. A compilation check, source-text assertion, or mock that assumes the desired outcome is not a reproducer. Add the regression to the routine local/pre-push and applicable CI suite before integration, push, or completion. In the routine suite a RED half may be gated by `agent_tools/tests/red_gate.py`: it reruns whenever no changed set is given (plain unittest runs and explicit audits) and whenever the test, its beforeimage or any file in its import or recorded-footprint closure changed; otherwise the runner skips it and records the skip with the digests of the unchanged test, beforeimage and closure. The GREEN half always runs, and a new or changed regression always proves its RED. Preserve the native scenario and rerun it against the fixed artifact. For behavior that only the OS can reproduce, still add the closest fast regression for the application-controlled decision, state transition, resource constraint, or failure response, and document precisely what remains covered only by native testing. Record the failure type, reproducer, failing/passing evidence, routine suite, and native evidence limits. Reproducible fixture, installer-harness, and workflow failures likewise require quick script or contract regressions. For native acceptance automation, add or update the related repository MCP workflow to detect, explain, or safely reconcile each discovered failure; preserve uncertainty rather than automatically replaying a mutation.


- **TEST-002 — Direct native proof before MCP integration.** For Windows, Android, Linux and macOS native acceptance, establish each required scenario directly with SSH, CLI, ADB or native platform tools outside MCP before adding or changing its MCP orchestration. Prove the complete scenario, including applicable success, failure, recovery and cleanup cases, with actual native evidence. Only after it passes, integrate the proven procedure into MCP and rerun the same cases through MCP against matching source/artifacts; direct success alone does not satisfy MCP acceptance. For Windows matrix rows the MCP rerun of a final evidence set is scoped to its route shapes: each route shape among the set's rows (plain, UAC approve, UAC deny, update, reboot pre, reboot post) needs a passed MCP run of some row with that shape, and the set's longest row (most job polls of its direct pass) and its row with the largest collected evidence each need their own passed MCP run; every other row counts with its direct pass and a passed MCP admission dry run of that pass (`mcp-admission`), which proves without running it that the MCP route takes that exact operation: the adapter's artifact keys, one local bundle-manifest location, its input resolvable at collect, the admission gates, and a repeat start that reaches the duplicate answer (the route's own executor started again on the real journal with a driver that refuses every call, so nothing is submitted or written). A failed or unknown run through either route still fails or holds its scenario. `matrix_observation` and `matrix-record` re-derive this rule from the evidence rows, and a passed record of a Windows requirement the driver maps must come from that evidence. Repeated MCP failures return the affected scenario to direct diagnosis rather than further unproved MCP attempts. Preserve TEST-001 causal regressions, exact source/artifact provenance, explicit file and environment ownership, protected state and credentials, durable original action identities and raw evidence, runtime-interruption authorization, and unknown-outcome non-replay rules in both phases. Repository startup and delivery still use the normal MCP workflow. A local test, diagnostic pass or component result does not prove a complete native scenario or authorize replay, weakened guards or a release.

- **TEST-003 — Parallel native acceptance with independent ownership.** Run independent Windows, Android, Linux and macOS native scenarios in parallel when their environment, state, file ownership and resource capacity permit it. Assign one operator to each guest/emulator and one writer to each file, recording the scenario, exact source/artifacts, environment, original process/job handle and cleanup owner. Separate guests or explicitly isolated state are required for scenarios that can interfere; installer, machine-wide VPN, reboot and fixture recovery operations sharing a guest serialize under its operator. A sole operator may batch independent read-only observations in one guest. Never clone an unverified live baseline or use a shared mutable package/workspace to manufacture independence. Observe existing handles through completion or unknown outcome before reusing their resources; timeouts do not authorize restart. Parallel scheduling preserves every acceptance case and both direct and MCP verification under TEST-002.

- **TEST-004 — Affected agent-tool checks and measured concurrency.** Product and prose-only changes run no agent-tool tests. Local selection is precise rather than complete: a tool or tool-owned dependency change runs the consumers that static imports, literal test and fixture paths, path-keyed declared scopes and the per-test footprints recorded in CI connect, including old-source consumers for deletion and rename; changed agent files no selected test reaches are reported, never silently treated as covered. A missing local comparison baseline refuses with an explanation; full agent-suite audits are explicit. Hosted CI is the completeness gate and gates instead of selecting: it runs no agent tests or, when any agent input changed or the comparison baseline is unavailable, the complete agent suite, partitioned across separate jobs by tracked measured module durations; every shard receipt and their exact disjoint union must verify. Record per-test duration and outcome. Concurrent groups require reviewed source-bound independence and isolated mutable fixtures; unreviewed groups serialize. Incomplete children, import and fixture failures cannot yield a successful receipt.

- **TEST-005 — Immutable engineering context and bounded observations.** Native engineering execution may remain on an explicitly qualified clean original source tree across proven unrelated tooling changes. Preserve the original package/source/version and all consumed source, artifact, guest, operator and server identities. Actual product bytes and repository-derived dependencies must be revalidated; callers cannot waive dirty state or declare their own dependency subset. A native dispatch runs only its computed source closure (CI requires each declared closure to equal the computed import, shipped-source and literal-source closure), and only when every closure file is tracked, unmodified, not hidden by assume-unchanged or skip-worktree, and byte-identical to a published commit: the merge-base of HEAD with `origin/dev`, or the tip of an origin `ci/*` candidate. Purely local, unpushed source is refused. A fixed-host route's proof names the symbol that holds or validates its host literal, which CI checks; no hand-maintained source digest stands in for this review. Engineering equivalence does not confer final current-source acceptance. Collect complete actual bounded results privately on the first terminal observation before projecting public summaries. Retain original receipts independently; overflow, partial output or uncertain collection stays UNKNOWN. Reuse existing compatible admitted batches, serialize interfering mutations and never replay an uncertain original action. Infrastructure changes require a demonstrated blocker or an explicitly requested optimization with causal local coverage. TEST-001 and TEST-002 remain required.

- **TEST-006 — Complete failure discovery and failed-first reruns.** Managed local check tiers and required CI workflows run every independent check and test to completion after a failure, so one pass reports the complete failure set. Only a failed explicit safety gate, such as the SSH-close gate, a source change during the pass, or cancellation stops the work that depends on it, and the pass stays failed. Required CI check steps run under `!cancelled()` once their own setup succeeded, and multi-task Gradle invocations use `--continue`. Fixing may begin at the first reported failure while the pass continues, but only against an immutable snapshot of the checked tree; edits never change a running pass. Each managed run records its failed checks. After a fix, rerun exactly those recorded failures first, with agent tests narrowed to their failed test modules; only when they pass, run the complete affected suite and pre-push tier. An unresolved recorded failure set refuses the pre-push tier, and a pre-push receipt only ever comes from one complete passing run of the final tree.

- **TEST-007 — Defect discovery before the final evidence sweep.** Native acceptance runs in two phases. In discovery, every new or changed scenario row gets one direct first-contact run as soon as its tooling exists, on a non-evidence build of the current candidate (for example its push-build package, never the frozen evidence package), so product and tool defects surface before final evidence is collected; each failure follows TEST-001, and tool patches may land between discovery runs. A settled failed or unknown run on the evidence package must stand beside any pass of its requirement for that source, so a discovery failure there blocks the requirement until a new package. The final sweep starts only once the candidate package and the scenario tooling are frozen, and only when `sweep-eligibility` on the candidate frozen set and the checkout's HEAD shows that a pass of every planned row would count: the set's source is HEAD or reaches it by an equivalence link (a limited record never links, so its source must be HEAD itself), no scenario of the swept requirements is unmapped, no row is refused or lacks a set artifact, no unretracted pass and no failure or unknown, retracted or not, is recorded for the requirement and source, and no settled failed or unknown run on the target package is unrecorded; a sweep it refuses does not start. Every required row then runs directly on that package, and the representative rows of TEST-002 also through MCP after their direct runs. MCP twins run only in the final sweep, and no tool or product change lands while one is in flight, because a source change during an MCP call makes it refuse and a changed bundle breaks its duplicate check. A recorded pass stays current at a later HEAD only through an equivalence link, which a change to an input the scenario executed ends: a product build input (product code, Gradle settings and build files, packaging scripts and workflows, `gradle.properties`, so a version roll), a file the scenario bundle table ships to the guest, or a module in the import closure of the host-side driver and classifier modules (every module importing the bundle, execution, matrix or equivalence module) or a resource they name. `native_artifact_reuse` derives these sets from each commit's own files; tests, Gradle test source sets, fixtures, selector metadata, docs and tools outside the closure do not end a link. A change that ends the link restarts the sweep for every row on a package built after it. A late product fix forces a rerun of every row, and an MCP twin in flight blocks every tool patch, so discovery runs go first and MCP twins go last.

## Release Contracts

- **RELEASE-001 — Development branch.** Normal work lands on `dev`, and only through the pre-merge CI gate: the candidate SHA is pushed to its own `ci/*` branch, and `dev` fast-forwards to that same SHA only after every required development workflow in `.github/required-workflows.json` has succeeded for it and only while `dev` is still its ancestor. A red, missing or pending result never reaches `dev`. The gate matches runs by exact SHA, so the fast-forward needs no second run. Each gate result is recorded first; a merged `ci/*` branch is then deleted on origin and locally at once, while a red, pending, rebase-needed or abandoned one is kept until cleanup finds it contained in `dev` or aged, and cleanup never deletes a branch with an unfinished run or one that has not had its runs yet. A `dev` push run may reuse a `ci/*` result only when the newest exact-SHA `ci/*` push run of that workflow succeeded. Work is reported complete only once `origin/dev` contains it. **Documentation-only equivalence:** a SHA with no exact runs of its own whose difference from a SHA with successful exact runs touches only documentation, as classified by the agent-test selector minus `README.md`, `docs/CHANGELOG.md` and `gradle.properties`, may reuse that result after the documentation checks (`git diff --check`, docs hygiene, source whitespace) pass on it; its own red, pending or partial runs, any non-documentation path (including `CLAUDE.md`, whose content a test asserts), any red, pending or partially run reference, or any failed documentation check requires its own exact-SHA runs. A release never uses this equivalence (`RELEASE-005`).
- **RELEASE-002 — Explicit authorization.** Building, finishing, shipping development work, or pushing does not authorize `main`, a tag, a GitHub Release, or stable publishing. Only an explicit user release command does.
- **RELEASE-003 — Unified version source.** `gradle.properties` owns one three-part product version for Android, Linux, Windows, macOS, GitHub releases, update metadata, README, and the latest versioned changelog heading. The major component is in `1..19`, the others are in `0..19`, and components carry at 20; a zero major is forbidden because the macOS packager rejects it. Platform-specific product-version projections are forbidden. Android `versionCode` and the update-manifest build number are internal monotonic IDs derived by appending one zero base-20 component; they are never displayed as product versions.
- **RELEASE-004 — Changelog roll.** Every non-documentation change adds one concise `Unreleased` bullet. The tenth bullet rolls the version with carry; an early forced roll is allowed only during an explicitly requested release.
- **RELEASE-005 — Exact-SHA release gates.** Release merge fast-forwards `main` from the already verified `origin/dev` SHA, which must itself have successful exact-SHA runs of every required workflow (a documentation-only equivalence does not qualify), dispatches exhaustive `VPN Integration / all`, and starts a full agent visual review for that SHA. Package workflows, exhaustive integration, the matching visual receipt, and its successful commit status must all succeed; for each package workflow the newest exact-SHA push run decides, and a package comes only from the unbroken run of successes below it. Release-ready sources never restore the Gradle User Home that development warm runs wrote, nor reuse cached task outputs.
- **RELEASE-006 — Publisher defense in depth.** The manual publisher independently verifies main/dev SHA equality, version/changelog metadata, exact-SHA package workflows, exhaustive VPN integration, the `vpn-control/agent-visual` status and receipt digest, stable Android signer, package contents, checksums, and update manifest before creating a new immutable tag/release.
- **RELEASE-007 — No same-SHA exception.** The agent reviews all captures and triages failures, but cannot approve an automated failure on the same SHA. There is no human approval override; fixes, baseline corrections, and test corrections return to `dev` and produce a new exact SHA.
