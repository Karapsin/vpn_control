## Local inventory and capture qualification

The pure local platform probe reports `infrastructureAvailable` and
`candidateKinds` for configured lifecycle candidates. These observations do not
qualify an interactive desktop or release capture. Without a source-owned
qualification consumer it reports `ready: false`, empty `capabilities` and
`qualificationState: unqualified` (or `unavailable` when no candidate exists).
The capture planner requires qualified capabilities. Explicit bootstrap and
start use infrastructure availability, so an existing stopped VM remains a
startup candidate and is not rebuilt because capture qualification is absent.
Actual capture retains its separate target, session and input admission checks.

### Fixed Secure Boot firmware prerequisite

`vm_workflow("windows-vm-virt-firmware-install-start", inputs=...)` is the
single remote installer for the Windows Secure Boot VM prerequisite. It accepts
only `{host: "archlinux", correlationId: "<canonical lowercase UUID>",
timeoutSeconds: 10..300}` and installs only `virt-firmware=26.9-1`. Its status
counterpart accepts the same exact fields and only observes the durable local
intent plus the fixed package identity and integrity checks.

Before any start, call `windows-vm-virt-firmware-install-preflight` with a new
canonical correlation and the same fixed host/timeout fields. It performs no
credential read and returns only `ready`, `intent-existing`,
`signature-policy-rejected`, `credential-metadata-invalid`, or
`signature-policy-unavailable`, or `transport-unavailable`. The categorical
transport diagnostic identifies the local SSH, gateway SSH, nested SSH, remote
Python, and `pacman-conf` hop without exposing raw stderr. A status call with no durable intent returns
`intent-absent`; it does not contact the host or manufacture a remote `unknown`.

The start route reads the local ignored `.codex/arch-sudo.local` file. It must
be a nonempty regular non-symlink file owned by the current POSIX user with mode
`0600` and at most 512 bytes. The credential never enters MCP fields, SSH/shell
arguments, environment variables, journals, stdout, stderr, or public results;
it is supplied only over SSH stdin to the fixed remote `sudo -S pacman` command.
The `.codex` parent is opened as a non-symlink directory descriptor before the
credential is opened. Before the credential is read or sent, the fixed remote
`/usr/bin/pacman-conf --repo extra SigLevel` check requires a package signature
token (`Required` or `PackageRequired`) and trusted-key token (`TrustedOnly` or
`PackageTrustedOnly`), rejecting `Never`/`PackageNever`, optional signatures,
and `TrustAll`.
The remote transaction uses pacman's configured signature verification, then
checks `pacman -Q virt-firmware`, `pacman -Qkk virt-firmware`, and executable
`/usr/bin/virt-fw-vars` before it can report `verified`.
The fixed transaction does not use `--needed`, so an already installed matching
version is reinstalled through pacman's signature verification.

Sudo and pacman diagnostics stay suppressed so credential bytes cannot enter
public logs. A nonzero fixed transaction therefore reports only
`transaction-failed`; it does not claim whether sudo authentication or pacman
caused the failure.

Start validates the local credential, then writes one owner-private intent before
SSH submission. An invalid local credential writes no intent. A duplicate start,
timeout, response loss, or `unknown` result is never replayed. Call
`windows-vm-virt-firmware-install-status` with the exact correlation instead;
its `replayAllowed: false` remains authoritative. This route does not copy a
live VM disk, open CP117, or start, stop, reset, or modify any VM.

The installer pins both the local and each configured nested SSH hop to
`/usr/bin/ssh`; remote Python is `/usr/bin/python3`. Its one fixed pacman target
is `extra/virt-firmware=26.9-1`.

### Fixed swtpm integrity repair for the Windows fixture

`vm_workflow("windows-vm-swtpm-repair-preflight", inputs=...)` and its one-shot

Preflight is read-only and does not read `.codex/arch-sudo.local`. It uses the

configured `extra` policy uses the same bounded `pacman-conf` evaluation as the
firmware repair: when `extra` inherits the global policy it checks that global

be reinstalled through pacman's signature verification. Remote stderr and
transaction diagnostics are discarded. The postcondition requires the exact
installed version and a passing `pacman -Qkk swtpm` with no active swtpm process.
The raw remote start rechecks exact package identity and `Qkk` before it reads
stdin; if another actor already repaired the package, it returns
`already-healthy` and makes no sudo or pacman transaction.

An accepted intent, timeout, response loss, or `unknown` result is never
replayed; use status with the same correlation. Results, SSH arguments,

### Fixed Windows credential recovery

Credential recovery uses owner-only opaque handles from `NativeCredentialStore`.
Every handle is bound to the exact `environment`, `accountName`, `expectedSid`,
purpose `account-login`, and one attempt `correlationId`; a handle cannot be read,
observed, or made active under another binding. The secret is generated and kept
under ignored `.runtime/native-credentials`; no secret is accepted in tool
arguments or returned in stdout/results. Earlier handles remain private audit
records after a later credential becomes active.

The optional `recoveryAdmission` field belongs inside the private
`windowsCredentialProbe` object shown above. When present, its field set is exact:

```json
"recoveryAdmission": {
  "taskName": "<owned-task-name>",
  "taskPath": "\\",
  "expectedLastResult": 0,
  "expectedTaskState": "Disabled",
  "expectedTaskExecute": "<approved-task-executable>",
  "expectedTaskPrincipal": "<approved-task-principal>",
  "expectedTaskArgumentsSha256": "<64 lowercase hex argument digest>"
}
```

These values admit one configured owned task only. The argument digest is stored
only in ignored private inventory; callers cannot provide task fields, an
executable, script, arguments, account data, or a credential. The durable recovery
intent retains the prior private credential reference and refuses publication if
that reference or the VM/account binding has changed.

`vm_workflow("windows-credential-recover-start", inputs=...)` and
`vm_workflow("windows-credential-recover-status", inputs=...)` require `host`,
`correlationId`, and optional integer `timeoutSeconds` from 1 through 60 (15 by
default). New starts also require an explicit `environment` matching the configured
Windows VM. `vm_workflow("credential-status", inputs=...)` accepts exactly
`host`, `correlationId`, and opaque `handle`; it reports availability plus the
bound environment, account name, SID, purpose, and correlation, never credential
bytes. `correlationId` must be a UUID.

```text
vm_workflow("windows-credential-recover-start", {
  "host": "<host-alias>", "environment": "<configured Windows environment>", "correlationId": "<new UUID>", "timeoutSeconds": 15
})
vm_workflow("windows-credential-recover-status", {
  "host": "<host-alias>", "correlationId": "<same UUID>", "timeoutSeconds": 15
})
vm_workflow("credential-status", {
  "host": "<host-alias>", "correlationId": "<same UUID>", "handle": "<opaque nc-... handle>"
})
```

Start records durable intent before its single fixed reset submission. For a lost
response, timeout, or `unknown` result, call recovery status with the same
correlation; never replay the reset. Once reset reaches a successful terminal
receipt, status may advance the authorized recovery by running the fixed
credential-validity verification. It observes an existing verification attempt
when present and does not reissue the password reset. Only successful fixed
verification updates the private inventory reference and publishes the active
handle. Inactive task state must match exactly (`Disabled` or `Ready`); queued or
running tasks are never admitted. A terminal `verified: true` response establishes
recovery; credential-file existence alone does not. Rejections report a bounded
admission stage without disclosing raw exceptions or secret values.

### Owned Android stale-proxy recovery

`vm_workflow("android-proxy-recover", inputs=...)` accepts exactly `host`, `device`,
`expectedPort` (1–65535), and a UUID `correlationId`. It uses the configured owned
API29 profile and fixed loopback host, requires an OFF owner with no active
operations, absent stored proxy fields, and fresh independent NetworkMonitor
refusal at the expected task port. It records private intent before the single
Android proxy-observer clear. Merely deleting stored settings does not establish
that Android's cached proxy has cleared.

Completion requires a clear broadcast and successful fresh network validation,
then restores absent fields only while they still equal the values written by
the clear operation. `vm_workflow("android-proxy-recovery-status", inputs=...)`
accepts exactly `host`, `device`, and the returned `identity`. Reused correlations
only observe; unknown results never trigger another clear. Full command streams
stay in private evidence; public output contains categorical results and identity.

### Configured guest routes

Nested host profiles may reference another nested gateway, up to four hosts in
one declared route. Each hop preserves quoted argument boundaries and strict
known-host checks; cycles, missing gateways and excessive routes are rejected.
`remoteConfigFile` is an optional absolute path to an agent-owned SSH config on
the preceding host. A nested hop requires that field or `remoteControlPath`.
For example, the private guest profile can use the configured Arch host as its
`gateway` and the disposable guest alias as `remoteHostAlias`, with its dedicated
remote config and known-host file. Keep all concrete paths in the ignored
inventory. This does not modify the remote user's normal SSH configuration.

Password/askpass handling resolves the first local connection host, even through
multiple hops; intermediate credentials are never substituted for that host.
Use a fresh MCP process or `mcp_tool.sh` after changing the inventory schema if
an existing server still has the older module loaded. Probe the exact guest and
verify its OS/package identity before assigning it a native scenario.

### Native artifact, bundle, and environment helpers

The helpers below are local coordination and evidence tools. They never search a
host, download an artifact, start a VM, submit a native scenario, or turn a
historical record into a current observation. A successful response is evidence
only in the scope stated by that action.

`vm_workflow("source-review-close", inputs={"manifestPath": absolute_path,
"manifestSha256": full_sha256})` authenticates explicit local review inputs.
Supported manifests use source/archive rows in `files`, relative pinned `files`,
absolute pinned `pins`/`inputs`, or a direct map of absolute paths to pins.
Mixed schemas are rejected. Archive-only reviews require an explicit
`packetManifestPath` and `packetManifestSha256`, or an authenticated listed
`proofPath` and `proofSha256` carrying current `sourcePins`. Do not combine those
options. The helper retains file and ancestor descriptors, verifies full hashes
and generations, and closes every identity after all reads. Actual credential and
private-binding files are excluded. It writes no evidence and returns
`SOURCE_ONLY` with native permission and product acceptance both false. A source
closure receipt does not grant native execution.

`vm_workflow("artifact-register", inputs=record)` stores immutable, content-derived
artifact evidence under the checkout's private agent state. A local record must
name one existing regular file with its exact `sha256` and `size`, and use
`evidenceClass: "local-verified"`; registration streams those local bytes once.
Remote metadata uses `evidenceClass: "unverified-remote"` plus a configured host
alias, an absolute remote POSIX path, and a receipt. It is never contacted or
verified by this API. Artifact IDs have the form `sha256-<digest>`.

`artifact-find` returns at most 100 historical index matches (20 by default) and
does not reread artifact bytes. Filter only by registered identity fields such as
`artifactId`, `platform`, `artifactKind`, `sha256`, `sourceSha`,
`sourceFingerprint`, or location evidence. Treat every result as historical until
`artifact-verify` reports `verification: "verified"` for local bytes. Verification
can instead report `mismatch`, `missing-or-unsafe`, or `unverified-remote`; none
of those states establishes usable bytes. An artifact may have more than one
registered location; when no unique local location exists, supply the returned
`locationId` to verify the intended evidence location.

```text
vm_workflow("artifact-register", {
  "platform": "linux", "artifactKind": "desktop-package",
  "localPath": "/staging/package.tar.gz", "sha256": "<64 lowercase hex>",
  "size": 123456, "evidenceClass": "local-verified", "sourceSha": "<git sha>"
})
vm_workflow("artifact-find", {"platform": "linux", "artifactKind": "desktop-package"})
vm_workflow("artifact-verify", {"artifactId": "sha256-<64 lowercase hex>"})
```

`vm_workflow("bundle-prepare", inputs={"scenarioId":
"linux-public-update-driver", "outputDirectory": "<fresh directory>"})`
creates an exclusive mode-0700 snapshot of the allowlisted scenario source,
writes a canonical manifest, and imports the staged entrypoint in isolation. The
output directory must not already exist. `bundle-verify` rereads a frozen bundle
against its exact manifest digest and rejects changed, unexpected, symlinked, or
non-allowlisted files. It does not run the scenario.

```text
vm_workflow("bundle-prepare", {
  "scenarioId": "linux-public-update-driver",
  "outputDirectory": "<fresh-private-bundle-directory>"
})
vm_workflow("bundle-verify", {
  "path": "<prepared-bundle-directory>", "manifestSha256": "<returned digest>"
})
```

Without `hostAlias`, `environment-status` summarizes caller-supplied receipts,
marks them fresh, stale or unknown, and never claims readiness. With a configured
`hostAlias`, it performs bounded SSH observation; optional `device`, `jobIdentity`
and `artifactId`/`locationId` add configured Android, existing-job and local-byte
checks. `requestedProbesReady` applies only to those probes. Use `observeHost: true` for a fixed Linux `/proc` memory and QEMU inventory
probe; optional `vmIdentity: {pid, startTicks}` verifies a selected live guest.
Unparseable allocations or incomplete process visibility withhold the admission
measurement. Caller-supplied facts remain separately labelled and never establish
readiness. The host receipt feeds `admit-plan` or reservation accounting; observation
alone does not allocate memory or start a VM.
`timeoutSeconds` is bounded at30 seconds; unknown outcomes do not cancel jobs.
`environment-reserve` atomically records capacity for a host/environment/operator
request, beginning in `pending`; pending reservations count against the host
budget. An idempotent retry returns the same opaque identity. A reservation may
move to `running` only with that exact identity and a complete mapping of running
allocations. Neither state starts a VM or authorizes a native action.
`environment-release` requires that exact opaque identity and refuses release
while its correlated active-job evidence is active, unavailable, stale, or
unknown. A lost observation must remain unknown; do not retry execution to clear
it.

`linux-vm-readonly-inventory` takes only `{host: "archlinux",
timeoutSeconds: 1..30}`. It inventories the two fixed historical Ubuntu/Arch

bounded guest process/job facts when reachable. Incomplete or ambiguous facts
remain unknown. The result always has `nativeActionAllowed: false`; it neither
boots a guest nor reserves capacity or admits an installer.
For a running guest, completeness requires the observed QEMU PID generation to
remain stable after the guest probe and its open socket FDs to own both the
loopback SSH listener and QMP socket. Matching command-line claims alone are
insufficient. An unreadable live guest PID also makes its process census
incomplete.

```text
vm_workflow("environment-status", {"observations": []})
vm_workflow("environment-reserve", {

    "runningConfiguredMemoryBytes": 0, "pressure": "normal", "swapUsedBytes": 0}

vm_workflow("environment-release", {"reservationId": "<returned id>",
  "token": "<returned token>", "hostAlias": "build-host",
  "environment": "windows-vm", "operator": "agent-a"})
```

### Fixed CP117 loopback forward

`ssh_workflow("forward-open", host="archlinux")` is intentionally not a general
forwarding API. It can only use the configured nested `archlinux` route to expose
the owned Windows VM's loopback VNC service through the fixed local loopback port

or unavailable, use `forward-status` with the same host; never replay an uncertain

recorded local SSH process/control state match and the endpoint returns a valid
VNC protocol banner. This checks connectivity without entering credentials. `forward-close` requires

a forward owned by this tool. It can return `close_pending` or `owner_unknown`; those are not

ssh_workflow("forward-open", host="archlinux")

### Durable fixed-scenario execution

`scenario-start`, `scenario-status`, `scenario-resume` and `scenario-collect` are
registered `vm_workflow` actions. The component execution scenario
`linux-public-update-preflight`: it transfers and imports the verified Linux
public-update driver bundle. It performs no product installation or VPN action;
its receipt is explicitly component evidence.

Register the prepared `native-scenario-manifest.json` as a local artifact first.
Start takes exactly `scenarioId`, configured `host`, `environment`, `bundleHash`,
`artifactIds: {"bundleManifest": "sha256-<manifest digest>"}`, and a unique
`correlationId`. The other three actions take exactly `{correlationId}`. The
private adapter resolves the registered manifest rather than accepting command,
script, executable or remote-directory arguments.

The journal precedes submission. A repeated start never launches a second job;
resume only observes its existing correlation. Terminal receipt verification binds
the plan, artifacts and actual process generation. Local bundle removal does not
prevent observation of an already submitted remote job. Missing or uncertain
receipts remain unknown. The installed-package recipe below has its own fixed
adapter; new scenarios require an explicit adapter and native evidence.

#### Windows scenarios

`agent_tools/native_scenario_windows.py` is the Windows adapter behind the same
four actions. `host` names the VM host and `environment` the deployment UUID, and
`correlationId` must be a canonical UUID. The closed list is the table
`native_scenario_windows.RECIPES`: `windows-ordinary-qualification`, a harmless
component row with no product and no package; three setup rows
(`windows-python-install`, `windows-msi-base-install`, `windows-msi-base-reset`);
three product rows (`windows-packaged-cli-smoke`, `windows-disconnected-cli-config`,
`windows-streaming-client-interrupt`); and the reboot, proxy-lifecycle and thirteen
`windows-public-update.<variant>` rows below. A name lands only with its case
module; the package rows have offline regressions, and their first native runs are
still their direct proof. The adapter refuses before any journal unless the name,
host, deployment, artifact keys and every bundle byte match this checkout, so a
caller cannot supply a path, argv, source or bytes.

One durable job, `agent_tools/windows_scenario_host_job.py`, runs on the VM host
and carries the stages: fence, read-only guest context, publish, requests, one
SYSTEM program that registers and runs an InteractiveToken LeastPrivilege task,
evidence and receipt. Its guest programs journal as flat
`direct-guest-<uuid>.{intent,ack,terminal}.json` in the VM root, so
`readiness-reboot` refuses while a job is open. A job exits 0 for passed, 1 for a
known failure and 2 when refused before any guest effect. Anything else, including
exit 3, is UNKNOWN: its fence stays open, no terminal is written, and new jobs and
reboots on that clone refuse. Recover by reading the original, never by resubmitting.

A row that was refused before it started has no receipt, so its collection stays
`unknown` with `executionExitCode` 2 and a closed `executionFailure` token. A setup
or component row never claims installed-package evidence.

Package rows name more artifacts at `scenario-start`. `windows-python-install`
takes `pythonInstaller`, admitted only by the hash and size the planner pins. The
other five take `scenarioInput` and the package their row names: `basePackage` for
the two MSI setup rows, `targetPackage` for the product rows. The scenario input is
a registered local artifact of platform `windows`, kind `scenario-input` and at
most 4,096 bytes: one JSON object with exactly `schema`
(`vpn-control.windows-scenario.input`), `schemaVersion` (1), `scenarioId`,
`correlationId` and `deploymentId` (this start's own), `sourceSha` (a full Git
SHA), `productVersion` (`a.b.c`), `artifactSetId` and `priorInstall`.
`priorInstall` is null on a setup row; a product row names the operation of a
passed `windows-msi-base-install` or `windows-msi-base-reset` on the same VM.

Package admission runs at `scenario-start` before any journal and again inside
submit. Each package must be a verified local registration with platform
`windows`, its role's fixed kind (`test-toolchain-installer` or `desktop-package`)
and at most 1 GiB. A desktop package must also be an `.msi` whose `sourceSha` is
the input's, and a member of the frozen set that `artifactSetId` names, verified
read-only, whose source is that SHA and whose product version equals the input's
`productVersion`. Refusals name `windows_scenario_input_*` or
`windows_scenario_package_*`, such as `windows_scenario_package_not_frozen` or
`windows_scenario_package_version`. These checks catch a mislabelled package, not
a substituted one: the registry and the set record what their caller registered.

Submit stages an admitted package before the job exists. It goes over SSH stdin
into the host's artifact cache,
`~/.cache/vpn-control-windows-scenarios/artifacts/<sha256>`: a check, then a write
into a private temporary file that is hashed and linked create-only, within 900 s.
A present, matching copy is never sent again. The staging program sets umask 077
itself and refuses an existing cache folder that other users can open. The job
plan names only digests and sizes, and the job pushes the bytes to the guest in
32,768-byte chunks. One transport admission covers every call of a submit and is
the sum of their budgets: 390 s without a package, 1,350 s with one. A lost reply
anywhere in submit, staging included, ends the start as
`submit_response_unavailable`; status and resume only look for it by
correlation, and nothing submits it again.

A product row pushes no MSI. Before its fence the job reads the named install's
receipt on the host and exits 2 unless that job passed on this VM with the same
package digest and product version (`prior_install_unavailable`,
`prior_install_other_package`). In the guest it then requires exactly one per-user
registration with that product code and version, installed in the install folder
(`installed_registration_differs`), and a complete installed-tree digest and file
count equal to the recorded ones (`installed_tree_differs`). The installed
application is pinned only in the worker request, so an MSI may replace its files.
The Python and installed trees are listed first and counted with the request's
fixed pins: above 4,096 file or 1,024 directory pins the row ends with the known
failure `worker_pin_bound`, before any tree pin and before any task.

`windows-python-install` refuses when the Python tree already exists
(`python_tree_present`). `windows-msi-base-install` refuses when any vpn-control
product is registered (`installed_product_state`) or when the install folder,
`%LOCALAPPDATA%\vpn-control`, already holds a file (`installed_files_present`;
empty folders do not count, as the tree digest counts only files).
`windows-msi-base-reset` is the VM's way back to a clean base: it needs exactly one
per-user registration, removes it with `msiexec /x` and the exact product code the
guest reported, then installs the admitted base as the install row does. Its
worker request also names `uninstallRoot`, the install folder, which the planner
requires inside LocalAppData, not LocalAppData itself, and apart from the
operation root. A failed removal installs nothing. If the removal left any file
there, the worker writes the event `uninstall-left-files` and exits 1 without
installing, and the receipt shows only `task_exit_code`. The VM then has no
product but files in that folder, so a base install refuses until someone clears
it; no tool route does.

The registration read runs as SYSTEM and enumerates every user and context at once
(`S-1-1-0`, context 7), keeping the ordinary user's rows and the machine's and
naming products by `InstalledProductName`, as the natively proven installed-context
reader does. A name it cannot read is counted, never dropped silently. A failed
receipt check names that check after a colon, as a finite code and never as guest
text: for example `publisher_msi_receipt:package_shape_list`,
`installed_product_state:count_0:considered_12:unnamed_0` or
`installed_registration_differs:location`.

A product row is `productAction` true and is `installed-package` evidence only
when the job is terminal, its collection complete, `windows.installedPackage` true
and `packageSha256` equal to the `targetPackage` ID. The receipt sets
`installedPackage` only for a passed product row whose registration and installed
tree matched and whose task passed its check. A stopped product row never claims
it: a job stopped early by `stop_after`, which only the direct script sets,
records `installedPackage` false and its `stoppedAfter`, and `public_evidence`
reads it as `installed-package-unproven` whatever else its receipt says.

Reboot rows come in pairs around `readiness-reboot`, which stays the only reboot
submitter: `windows-reboot-reconnect.pre|.post`, `windows-reboot-explicit-off.pre|.post`
and `windows-autostart-migration.pre|.post`. Each `.pre` runs the
`windows-preboot-reboot` worker action in a fresh product workspace: an in-guest
SOCKS upstream on loopback port 41081, the owned profile (source set before the
first location), autostart migration from a legacy HighestAvailable task to the
public LeastPrivilege one, then a graceful quit of its own serve. It then starts
the app through the product's own autostart task, measures traffic for reconnect,
stops its upstream and finishes with the app running and no child of its own. A
passed `.pre` publishes `product-allowance.json` into its own ProgramData workspace
through the SYSTEM publisher (stage `declare`); its receipt's `preboot` part names
the workspace, the checkpoint event and the boot time. The package has no loose
runtime: it ships inside an app jar and is extracted per workspace, so every reboot
row takes the runtime digest from `runtimeAuthority` in the installed
`app\native\windows-amd64\native-helpers.json`. The job reads that file's bytes
once over the agent against its installed-tree pin; the guest action reads the same
held file. A missing or malformed record is the known failure
`installed_runtime_authority` at publish.

Each `.post` is a new operation whose `scenarioInput` names its `.pre` in
`priorPreboot` (only `.post` inputs carry that field). It refuses with exit 2 and no
guest program unless that `.pre` passed on the same install record and package
(`prior_preboot_other_install` otherwise), and unless exactly one
`readiness-recovery-<id>` reboot journal in the VM root was submitted from the
`.pre`'s boot with an idle census that knew every declared product process
(`prior_preboot_reboot_unproven` otherwise: a crash or a restart is no reboot of the
pair). It then refuses after its read-only context unless the guest's boot FILETIME
is later than the `.pre`'s (`preboot_boot_not_newer`): the kernel boot identifier is
the same on every boot of a clone. Its receipt's `reboot.readinessReboot` names that
journal's recovery and operation IDs. It runs `windows-postboot-final` on the same
workspace: the startup census before any query, the task ran this boot, the GUI and
controller are the launcher-plus-JVM tree under the ordinary token, reconnect or off
held, GUI show and hide, traffic for reconnect, then autostart off and quit.
`windows-query-owner-gui-reconnect` is rebootless: `status` with no owner never
starts one, so a config query (`locations list`) starts a transient owner that never
connects, then a GUI restores the remembered intent once. All of these are product
rows that name their `priorInstall` and `targetPackage`.

One reboot chain runs at a time on a machine. Every reboot row's receipt has a
`reboot` part; for a `.pre` its `autostart` is `changed` when the owner's journal
holds an autostart or product-start intent, `untouched` when the owner never ran or
never got that far, and `unknown` when its evidence could not be read. A `.pre` that
is not `untouched` holds the machine until a passed `.post` names it: meanwhile
every other reboot row is refused with `reboot_chain_open`, and a `.post` for a
closed `.pre` with `prior_preboot_unavailable`. A prior job of the machine without a
readable receipt refuses every reboot row with `reboot_chain_unknown`. A failed `.pre`
that changed autostart may have left the legacy task or the app behind, so nothing
closes it on that clone; a new attempt is a new operation on another clone. A known refusal in
either action retires what the owner still runs: the owned upstream, then the
`.pre`'s own serve or the query GUI through the same journaled public quit to its
controller. The owner then finishes with exit 1; only an effect whose outcome was not
observed parks.

The order on one VM: package and install setup, then `.pre`, collect,
`readiness-reboot`, `readiness-ensure` (the sign-in fires the logon trigger), then
`.post`. The idle census lets the reboot through with the app running only for a
current-boot declaration (see `readiness_windows_idle.ALLOWANCE`); `consent.exe`, the
CLI and every undeclared process still block. Known gaps: the GUI tray, natively
unproven process shapes and the start of the task from a standard user are first
native contact; `windows-document-responsive` has its tools but no row yet, because
its TLS certificate, key and trust store have no producer.

`windows-proxy-lifecycle.<variant>` has one row per variant
`windows_ordinary_dedicated_driver.py` accepts for that action: `gui-pending`,
`find-best-success`, `find-best-verification-failure`, `find-best-cancel`,
`generated`, `custom`, `large`, `prepare-failure`, `commit-readiness-failure` and
`sibling-off`. `no-tray-close` and `scheduled-refresh` have no row, because the
driver refuses them. Inputs are those of every product row: the bundle manifest,
`targetPackage`, and a `scenarioInput` whose `priorInstall` names the passed
`windows-msi-base-install` or `windows-msi-base-reset` of that same package on
this VM. An absent, malformed or self-referencing `priorInstall` refuses before
any journal; one that names no passed install of this package on this VM is
refused by the job with exit 2, after the journal and before any guest effect.
The job publishes the driver's reviewed roles (driver, lifecycle cases,
runtime stages, observer, fixture worker, both loopback fixtures, and for
`gui-pending` and the six branch variants the traffic sampler, with the branch
cases and listener script for the branch variants). It extracts the bundled
`sing-box.exe` from the one installed jar that holds it, through a pin equal to
the installed tree's, and makes a literal harness, a self-signed `localhost`
certificate and key, a JKS trust store and the sampler's input. The key is made on
the VM host and lives only in the job's memory and the guest workspace: the QGA
wire files keep replies, never the write requests that carry it, and it never
enters evidence. The fixtures run in the guest on loopback, as the ordinary
user's children, started and stopped by the row. Evidence is that of every
product row: `installed-package` only from a passed, unstopped run whose MSI
registration and complete installed tree still match its prior install and whose
installed launcher, run under the ordinary token, answered `--help` and reported
the admitted version to `--version`. The driver asks before the row's runtime
starts, and another version ends the row 1. All ten variants can share one
installed base. A reviewed oracle failure closes what the row started and ends
1; an unknown outcome parks and ends UNKNOWN as before. The closing issues its
own off and quit, so an off that left the runtime running, or a refused quit,
goes out once more; a fixture that already ended keeps its own terminal.

Known before any native run: the relaunched launcher pair, the launcher's
`--help` and `--version` output through it, the extraction action, the generated
material in the product's JVM, GUI windows, close-to-tray and the crash path are
proved only offline. The loopback fixture keeps its 0.25 s TLS
handshake bound, which a slow guest JVM could miss; a find-best row would then end
a known failure, not UNKNOWN. The `gui-pending` sampler runs about six minutes,
so a longer GUI sequence also ends a known failure. The fixture's lease is
1,800 s, the most the runtime stages allow, while the row deadline is 3,600 s: a
row whose work after its fixture started outlives the lease loses its fixture and
ends a known failure.

`windows-public-update.<variant>` runs one `update_cases` variant through the
dedicated driver as the ordinary user. The update server, its CONNECT proxy and
the test-only trust store live in the guest on `127.0.0.1`; nothing listens on the
VM host or the controller. Inputs:

- Artifacts `targetPackage` (the target MSI) and `fixtureReceipt` (kind
  `desktop-update-fixture-receipt`), both from one frozen set at the input's
  `sourceSha`. The receipt is the CI fixture pair's `fixture-receipt.json`: test
  only, production trust unchanged, base and target built from one source, and a
  manifest whose single asset is the admitted target MSI.
- `baseVersion`, the installed version the update starts from: older than
  `productVersion` and never `2.2.13`, since the planner keeps expanded cases off
  that baseline (`windows_scenario_update_base_baseline`).
- `priorInstall`, the `windows-msi-base-reset` that installed that base, and
  `targetInstall`, an earlier `windows-msi-base-install` or `windows-msi-base-reset`
  of the same target MSI, whose job recorded the installed tree the update must
  leave. The fixture pair's own base build cannot be that base: a frozen set
  records its source's canonical version, so the reset installs an older MSI built
  at a commit whose canonical version is `baseVersion`, from that commit's own
  frozen set.

The job seals the served MSI read-only, makes a fresh TLS pair in the guest and
builds the trust store on the host from the public certificate only. It reads the
base's MSI registration with the reader the first native installs proved (one
enumeration of every user and context, by `InstalledProductName`), which also
reports each row's package code. Admitted: `public-ready`, `download-cancelled` and
`checksum-rejected`, which raise no prompt and need no SYSTEM collector. Refused
before any journal:

- the seven grant variants (`install-cancelled`, `participating-copy-lock`,
  `success-off`, `success-reconnect`, `different-admin`, `wait-client-loss`,
  `installer-wait-client-loss`) with `windows_scenario_update_grant_unproven`. No
  stage of this job discovers the elevated helper coordinator and its worker, so
  no collector proves the helper image and the approving SID.
- `native-install-failed` and `protected-storage-rejected` with
  `windows_scenario_update_fault_unavailable`. Nothing produces their faults: the
  product's MSIs carry no LaunchCondition table to fault, and nothing creates or
  removes a counterfeit protected-storage root.
- `uac-denied` with `windows_scenario_update_collector_unproven`. Its SYSTEM
  collector cannot run natively yet. The pinned collector chain takes its request
  file only as `O:SYD:P(...)`, but a file the publisher creates and then protects
  reads back `O:SYD:PAI(...)` (every native `worker-request.json` pin so far), so
  the job would end at publish with `collector_file_policy`. Its `terminal-actors`
  stage also reads the product's not-started disposition as SYSTEM, while the
  product writes that file for its owner alone and nothing on this route enables
  `SeBackupPrivilege`. Both a request writer and a reader have to be proved
  natively before the row is admitted.

The job keeps the collector stage engine for that day. A row with collector
stages serves `before-install` and then `terminal-actors` behind the caller's
close hold, inside its run. The owner names each need with an
`update-native-observation-needed` event. The job renders the collector from
`windows_system_collector`, runs it on the stdin route and then releases the hold.
It serves a need only while the run is open and the same status names no parked
file: a parked owner is reported and never touched, and a need read after the run
returned starts nothing. A stage the row cannot serve, or a collector that never
returns, ends UNKNOWN with the fence open. The status keeps
`uac-pending:install-helper:deny` from the owner's prompt event until the
decision's input terminal exists, however many events follow it. Collect passes
a deny row only when that terminal reads `input-ack-only`, `deny`,
`install-helper` and `promptClosed: true`. Without it the collection stays
`unknown`. Update rows never claim installed-package evidence, because no
`--version` runs under the ordinary token there.

Nothing in this family has reached a guest yet. The guest's Windows PowerShell
5.1 still has to prove the TLS pair (`CertificateRequest`, `RSACng` export), and
the product JVM has to open the generated trust store. An update row's
`priorInstall` and `targetInstall` must be installs made by this code: an earlier
install record has no package code and no installed inventory, so the job refuses
it before its fence (`prior_install_other_package`, `target_install_other_package`,
`target_install_inventory`).

#### Windows UAC decision

`vm_workflow windows-uac-decision` takes exactly `host`, `environment`,
`correlationId`, `prompt` (`install-helper` or `vpn-broker`) and `decision`
(`approve` or `deny`). It answers the one prompt of a running scenario whose
dotted name is in the closed table of `agent_tools/windows_uac_decision.py`, and
only when that row's prompt and decision equal the inputs. A row whose owner
published its prompt event reports `uac-pending:<prompt>:<decision>` in
`scenario-status`; a fixed client polls for it, because a model turn may not fit
the prompt's lifetime. The job and the owner never call or wait on this action.
The token outlives the prompt, so the client may call on every poll: a refusal
that proved only "not yet" (event not pending, a failed guest read, a busy lock,
nothing sent) permits another submit; any other refusal, such as no prompt
within the 30 s gate, leaves the prompt to expire, and a repeat returns that
refusal with no packet. A deny row is admitted at `scenario-start` only where
collect joins the decision's input terminal, because an expired prompt ends as the
same public `CANCELLED` as Esc. `windows-public-update.uac-denied` has that join
but is refused today for its collector (above).

Proof comes before any key: reviewed pixel crops of a QMP frame and a SYSTEM
census of `consent.exe` (one, System32, signed by Microsoft Windows, parent
Appinfo, younger than 90 s), the owner's pending event and the UAC policy. The
90 s rule holds at the burn, counting frames read after the census, and a dark
field is read again within the gate, since the caret blinks there. Deny is
one Esc and opens no credential. Approve reads `final-administrator.secret` through
`SecretFile` and passes it on SSH stdin to a detached child. A create-only burn per
prompt and the input journal precede the first key, so a lost reply never types
twice; a repeat is a status packet with no key path. The reply is an
acknowledgement only: `approvalSucceeded` and `productOutcomeProved` are always
false, and the scenario's own collection proves the product outcome. Profiles are
private, under `.runtime/windows-uac-profiles/<deployment>/<prompt>.json`, made by
`reviewed_uac_profile` from a frame the reviewer opened. Guest files stay under the
VM-root subdirectory `windows-uac/`, published whole, and the fence is a flat
`direct-guest-*` journal, so `readiness-reboot` refuses while input is open and
sign-in history never sees them. A known input closes the fence, and status
closes it if that close was lost. An input whose owner died stays UNKNOWN:
status records `input-outcome-unknown` once the prompt is gone but never closes
the fence, so reboots and new jobs on that clone refuse until the original is
read. No sign-in source pin moves, and the module is not alias-pinned.
