## Local inventory and capture qualification

The pure local platform probe reports `infrastructureAvailable` and
`candidateKinds` for configured lifecycle candidates. These observations do not
qualify an interactive desktop or release capture. Without a source-owned
qualification consumer it reports `ready: false`, empty `capabilities` and
`qualificationState: unqualified` (or `unavailable` when no candidate exists).
The capture planner requires qualified capabilities. Explicit bootstrap and
start use infrastructure availability, so an existing stopped VM remains a
startup candidate and is not rebuilt because capture qualification is absent.
Actual capture retains its separate target, session and input admission checks.

### Fixed Secure Boot firmware prerequisite

`vm_workflow("windows-vm-virt-firmware-install-start", inputs=...)` is the
single remote installer for the Windows Secure Boot VM prerequisite. It accepts
only `{host: "archlinux", correlationId: "<canonical lowercase UUID>",
timeoutSeconds: 10..300}` and installs only `virt-firmware=26.9-1`. Its status
counterpart accepts the same exact fields and only observes the durable local
intent plus the fixed package identity and integrity checks.

Before any start, call `windows-vm-virt-firmware-install-preflight` with a new
canonical correlation and the same fixed host/timeout fields. It performs no
credential read and returns only `ready`, `intent-existing`,
`signature-policy-rejected`, `credential-metadata-invalid`, or
`signature-policy-unavailable`, or `transport-unavailable`. The categorical
transport diagnostic identifies the local SSH, gateway SSH, nested SSH, remote
Python, and `pacman-conf` hop without exposing raw stderr. A status call with no durable intent returns
`intent-absent`; it does not contact the host or manufacture a remote `unknown`.

The start route reads the local ignored `.codex/arch-sudo.local` file. It must
be a nonempty regular non-symlink file owned by the current POSIX user with mode
`0600` and at most 512 bytes. The credential never enters MCP fields, SSH/shell
arguments, environment variables, journals, stdout, stderr, or public results;
it is supplied only over SSH stdin to the fixed remote `sudo -S pacman` command.
The `.codex` parent is opened as a non-symlink directory descriptor before the
credential is opened. Before the credential is read or sent, the fixed remote
`/usr/bin/pacman-conf --repo extra SigLevel` check requires a package signature
token (`Required` or `PackageRequired`) and trusted-key token (`TrustedOnly` or
`PackageTrustedOnly`), rejecting `Never`/`PackageNever`, optional signatures,
and `TrustAll`.
The remote transaction uses pacman's configured signature verification, then
checks `pacman -Q virt-firmware`, `pacman -Qkk virt-firmware`, and executable
`/usr/bin/virt-fw-vars` before it can report `verified`.
The fixed transaction does not use `--needed`, so an already installed matching
version is reinstalled through pacman's signature verification.

Sudo and pacman diagnostics stay suppressed so credential bytes cannot enter
public logs. A nonzero fixed transaction therefore reports only
`transaction-failed`; it does not claim whether sudo authentication or pacman
caused the failure.

Start validates the local credential, then writes one owner-private intent before
SSH submission. An invalid local credential writes no intent. A duplicate start,
timeout, response loss, or `unknown` result is never replayed. Call
`windows-vm-virt-firmware-install-status` with the exact correlation instead;
its `replayAllowed: false` remains authoritative. This route does not copy a
live VM disk, open CP117, or start, stop, reset, or modify any VM.

The installer pins both the local and each configured nested SSH hop to
`/usr/bin/ssh`; remote Python is `/usr/bin/python3`. Its one fixed pacman target
is `extra/virt-firmware=26.9-1`.

### Fixed swtpm integrity repair for the Windows fixture

transaction diagnostics are discarded. The postcondition requires the exact
installed version and a passing `pacman -Qkk swtpm` with no active swtpm process.
The raw remote start rechecks exact package identity and `Qkk` before it reads
stdin; if another actor already repaired the package, it returns

### Fixed Windows credential recovery

Credential recovery uses owner-only opaque handles from `NativeCredentialStore`.
Every handle is bound to the exact `environment`, `accountName`, `expectedSid`,
purpose `account-login`, and one attempt `correlationId`; a handle cannot be read,
observed, or made active under another binding. The secret is generated and kept
under ignored `.runtime/native-credentials`; no secret is accepted in tool
arguments or returned in stdout/results. Earlier handles remain private audit
records after a later credential becomes active.

The optional `recoveryAdmission` field belongs inside the private
`windowsCredentialProbe` object shown above. When present, its field set is exact:

```json
"recoveryAdmission": {
  "taskName": "<owned-task-name>",
  "taskPath": "\\",
  "expectedLastResult": 0,
  "expectedTaskState": "Disabled",
  "expectedTaskExecute": "<approved-task-executable>",
  "expectedTaskPrincipal": "<approved-task-principal>",
  "expectedTaskArgumentsSha256": "<64 lowercase hex argument digest>"
}
```

These values admit one configured owned task only. The argument digest is stored
only in ignored private inventory; callers cannot provide task fields, an
executable, script, arguments, account data, or a credential. The durable recovery
intent retains the prior private credential reference and refuses publication if
that reference or the VM/account binding has changed.

`vm_workflow("windows-credential-recover-start", inputs=...)` and
`vm_workflow("windows-credential-recover-status", inputs=...)` require `host`,
`correlationId`, and optional integer `timeoutSeconds` from 1 through 60 (15 by
default). New starts also require an explicit `environment` matching the configured
Windows VM. `vm_workflow("credential-status", inputs=...)` accepts exactly
`host`, `correlationId`, and opaque `handle`; it reports availability plus the
bound environment, account name, SID, purpose, and correlation, never credential
bytes. `correlationId` must be a UUID.

```text
vm_workflow("windows-credential-recover-start", {
  "host": "<host-alias>", "environment": "<configured Windows environment>", "correlationId": "<new UUID>", "timeoutSeconds": 15
})
vm_workflow("windows-credential-recover-status", {
  "host": "<host-alias>", "correlationId": "<same UUID>", "timeoutSeconds": 15
})
vm_workflow("credential-status", {
  "host": "<host-alias>", "correlationId": "<same UUID>", "handle": "<opaque nc-... handle>"
})
```

Start records durable intent before its single fixed reset submission. For a lost
response, timeout, or `unknown` result, call recovery status with the same
correlation; never replay the reset. Once reset reaches a successful terminal
receipt, status may advance the authorized recovery by running the fixed
credential-validity verification. It observes an existing verification attempt
when present and does not reissue the password reset. Only successful fixed
verification updates the private inventory reference and publishes the active
handle. Inactive task state must match exactly (`Disabled` or `Ready`); queued or
running tasks are never admitted. A terminal `verified: true` response establishes
recovery; credential-file existence alone does not. Rejections report a bounded
admission stage without disclosing raw exceptions or secret values.

### Owned Android stale-proxy recovery

`vm_workflow("android-proxy-recover", inputs=...)` accepts exactly `host`, `device`,
`expectedPort` (1–65535), and a UUID `correlationId`. It uses the configured owned
API29 profile and fixed loopback host, requires an OFF owner with no active
operations, absent stored proxy fields, and fresh independent NetworkMonitor
refusal at the expected task port. It records private intent before the single
Android proxy-observer clear. Merely deleting stored settings does not establish
that Android's cached proxy has cleared.

Completion requires a clear broadcast and successful fresh network validation,
then restores absent fields only while they still equal the values written by
the clear operation. `vm_workflow("android-proxy-recovery-status", inputs=...)`
accepts exactly `host`, `device`, and the returned `identity`. Reused correlations
only observe; unknown results never trigger another clear. Full command streams
stay in private evidence; public output contains categorical results and identity.

### Configured guest routes

Nested host profiles may reference another nested gateway, up to four hosts in
one declared route. Each hop preserves quoted argument boundaries and strict
known-host checks; cycles, missing gateways and excessive routes are rejected.
`remoteConfigFile` is an optional absolute path to an agent-owned SSH config on
the preceding host. A nested hop requires that field or `remoteControlPath`.
For example, the private guest profile can use the configured Arch host as its
`gateway` and the disposable guest alias as `remoteHostAlias`, with its dedicated
remote config and known-host file. Keep all concrete paths in the ignored
inventory. This does not modify the remote user's normal SSH configuration.

Password/askpass handling resolves the first local connection host, even through
multiple hops; intermediate credentials are never substituted for that host.
Use a fresh MCP process or `mcp_tool.sh` after changing the inventory schema if
an existing server still has the older module loaded. Probe the exact guest and
verify its OS/package identity before assigning it a native scenario.

### Native artifact, bundle, and environment helpers

The helpers below are local coordination and evidence tools. They never search a
host, download an artifact, start a VM, submit a native scenario, or turn a
historical record into a current observation. A successful response is evidence
only in the scope stated by that action.

`vm_workflow("source-review-close", inputs={"manifestPath": absolute_path,
"manifestSha256": full_sha256})` authenticates explicit local review inputs.
Supported manifests use source/archive rows in `files`, relative pinned `files`,
absolute pinned `pins`/`inputs`, or a direct map of absolute paths to pins.
Mixed schemas are rejected. Archive-only reviews require an explicit
`packetManifestPath` and `packetManifestSha256`, or an authenticated listed
`proofPath` and `proofSha256` carrying current `sourcePins`. Do not combine those
options. The helper retains file and ancestor descriptors, verifies full hashes
and generations, and closes every identity after all reads. Actual credential and
private-binding files are excluded. It writes no evidence and returns
`SOURCE_ONLY` with native permission and product acceptance both false. A source
closure receipt does not grant native execution.

`vm_workflow("artifact-register", inputs=record)` stores immutable, content-derived
artifact evidence under the checkout's private agent state. A local record must
name one existing regular file with its exact `sha256` and `size`, and use
`evidenceClass: "local-verified"`; registration streams those local bytes once.
Remote metadata uses `evidenceClass: "unverified-remote"` plus a configured host
alias, an absolute remote POSIX path, and a receipt. It is never contacted or
verified by this API. Artifact IDs have the form `sha256-<digest>`.

`artifact-find` returns at most 100 historical index matches (20 by default) and
does not reread artifact bytes. Filter only by registered identity fields such as
`artifactId`, `platform`, `artifactKind`, `sha256`, `sourceSha`,
`sourceFingerprint`, or location evidence. Treat every result as historical until
`artifact-verify` reports `verification: "verified"` for local bytes. Verification
can instead report `mismatch`, `missing-or-unsafe`, or `unverified-remote`; none
of those states establishes usable bytes. An artifact may have more than one
registered location; when no unique local location exists, supply the returned
`locationId` to verify the intended evidence location.

```text
vm_workflow("artifact-register", {
  "platform": "linux", "artifactKind": "desktop-package",
  "localPath": "/staging/package.tar.gz", "sha256": "<64 lowercase hex>",
  "size": 123456, "evidenceClass": "local-verified", "sourceSha": "<git sha>"
})
vm_workflow("artifact-find", {"platform": "linux", "artifactKind": "desktop-package"})
vm_workflow("artifact-verify", {"artifactId": "sha256-<64 lowercase hex>"})
```

`vm_workflow("bundle-prepare", inputs={"scenarioId":
"linux-public-update-driver", "outputDirectory": "<fresh directory>"})`
creates an exclusive mode-0700 snapshot of the allowlisted scenario source,
writes a canonical manifest, and imports the staged entrypoint in isolation. The
output directory must not already exist. `bundle-verify` rereads a frozen bundle
against its exact manifest digest and rejects changed, unexpected, symlinked, or
non-allowlisted files. It does not run the scenario.

```text
vm_workflow("bundle-prepare", {
  "scenarioId": "linux-public-update-driver",
  "outputDirectory": "<fresh-private-bundle-directory>"
})
vm_workflow("bundle-verify", {
  "path": "<prepared-bundle-directory>", "manifestSha256": "<returned digest>"

```

Without `hostAlias`, `environment-status` summarizes caller-supplied receipts,
marks them fresh, stale or unknown, and never claims readiness. With a configured

and `artifactId`/`locationId` add configured Android, existing-job and local-byte
checks. `requestedProbesReady` applies only to those probes. Use `observeHost: true` for a fixed Linux `/proc` memory and QEMU inventory
probe; optional `vmIdentity: {pid, startTicks}` verifies a selected live guest.
Unparseable allocations or incomplete process visibility withhold the admission

readiness. The host receipt feeds `admit-plan` or reservation accounting; observation
alone does not allocate memory or start a VM.
`timeoutSeconds` is bounded at30 seconds; unknown outcomes do not cancel jobs.
`environment-reserve` atomically records capacity for a host/environment/operator

`environment-release` requires that exact opaque identity and refuses release

`linux-vm-readonly-inventory` takes only `{host: "archlinux",

### Fixed CP117 loopback forward

`ssh_workflow("forward-open", host="archlinux")` is intentionally not a general

### Durable fixed-scenario execution

`scenario-start`, `scenario-status`, `scenario-resume` and `scenario-collect` are
registered `vm_workflow` actions. The component execution scenario
`linux-public-update-preflight`: it transfers and imports the verified Linux
public-update driver bundle. It performs no product installation or VPN action;
its receipt is explicitly component evidence.

Register the prepared `native-scenario-manifest.json` as a local artifact first.
Start takes exactly `scenarioId`, configured `host`, `environment`, `bundleHash`,
`artifactIds: {"bundleManifest": "sha256-<manifest digest>"}`, and a unique
`correlationId`. The other three actions take exactly `{correlationId}`. The
private adapter resolves the registered manifest rather than accepting command,
script, executable or remote-directory arguments.

The journal precedes submission. A repeated start never launches a second job;
resume only observes its existing correlation. Terminal receipt verification binds
the plan, artifacts and actual process generation. Local bundle removal does not
prevent observation of an already submitted remote job. Missing or uncertain
receipts remain unknown. The installed-package recipe below has its own fixed
adapter; new scenarios require an explicit adapter and native evidence.

#### Windows scenarios

`agent_tools/native_scenario_windows.py` is the Windows adapter behind the same
four actions. `host` names the VM host and `environment` the deployment UUID, and
`correlationId` must be a canonical UUID. The closed list is the table
`native_scenario_windows.RECIPES`: `windows-ordinary-qualification`, a harmless
component row with no product and no package; three setup rows
(`windows-python-install`, `windows-msi-base-install`, `windows-msi-base-reset`);
five product rows (`windows-packaged-cli-smoke`, `windows-disconnected-cli-config`,
its variants `windows-disconnected-cli-config.ssh-import-routing` and
`windows-disconnected-cli-config.ssh-relay-transfer`, and
`windows-streaming-client-interrupt`); and the reboot, proxy-lifecycle, four
`windows-scoped-tun.<variant>`, thirteen `windows-public-update.<variant>` and six
document rows below. A name lands only with its case
module; the package rows have offline regressions, and their first native runs are
still their direct proof. The adapter refuses before any journal unless the name,
host, deployment, artifact keys and every bundle byte match this checkout, so a
caller cannot supply a path, argv, source or bytes.

One durable job, `agent_tools/windows_scenario_host_job.py`, runs on the VM host
and carries the stages: fence, read-only guest context, publish, requests, one
SYSTEM program that registers and runs an InteractiveToken LeastPrivilege task,
evidence and receipt. Its guest programs journal as flat
`direct-guest-<uuid>.{intent,ack,terminal}.json` in the VM root, so
`readiness-reboot` refuses while a job is open. A job exits 0 for passed, 1 for a
known failure and 2 when refused before any guest effect. Anything else, including
exit 3, is UNKNOWN: its fence stays open, no terminal is written, and new jobs and
reboots on that clone refuse. Recover by reading the original, never by resubmitting.

A row that was refused before it started has no receipt, so its collection stays
`unknown` with `executionExitCode` 2 and a closed `executionFailure` token. A setup
or component row never claims installed-package evidence.

Package rows name more artifacts at `scenario-start`. `windows-python-install`
takes `pythonInstaller`, admitted only by the hash and size the planner pins. The
other five take `scenarioInput` and the package their row names: `basePackage` for
the two MSI setup rows, `targetPackage` for the product rows. The scenario input is
a registered local artifact of platform `windows`, kind `scenario-input` and at
most 4,096 bytes: one JSON object with exactly `schema`
(`vpn-control.windows-scenario.input`), `schemaVersion` (1), `scenarioId`,
`correlationId` and `deploymentId` (this start's own), `sourceSha` (a full Git
SHA), `productVersion` (`a.b.c`), `artifactSetId` and `priorInstall`.
`priorInstall` is null on a setup row; a product row names the operation of a
passed `windows-msi-base-install` or `windows-msi-base-reset` on the same VM.

Package admission runs at `scenario-start` before any journal and again inside
submit. Each package must be a verified local registration with platform
`windows`, its role's fixed kind (`test-toolchain-installer` or `desktop-package`)
and at most 1 GiB. A desktop package must also be an `.msi` whose `sourceSha` is
the input's, and a member of the frozen set that `artifactSetId` names, verified
read-only, whose source is that SHA and whose product version equals the input's
`productVersion`. Refusals name `windows_scenario_input_*` or
`windows_scenario_package_*`, such as `windows_scenario_package_not_frozen` or
`windows_scenario_package_version`. These checks catch a mislabelled package, not
a substituted one: the registry and the set record what their caller registered.

Submit stages an admitted package before the job exists. It goes over SSH stdin
into the host's artifact cache,
`~/.cache/vpn-control-windows-scenarios/artifacts/<sha256>`: a write into a private
temporary file that is hashed and linked create-only, within 900 s. A present,
matching copy is never sent again. The staging program sets umask 077 itself and
refuses an existing cache folder that other users can open. The job plan names
only digests and sizes, and the job pushes the bytes to the guest in 32,768-byte
chunks.

The cache is shared by every submit to the host, so another operator can stage
the same digest between this submit's read and its write. The write then answers
`present` instead of `staged`, and submit accepts either one. `present` is said
only after the staging program has hashed the cached copy and found it regular,
owned by the account, mode 0600, and of this size and digest. A copy that
`differs` still refuses, and nothing is written over it.

A guest push that fails is `guest_file_push_lost`, and its chunk is never written
again. The receipt's `push` names the cause: the call (`guest-file-open`,
`guest-file-write`, `guest-file-close` or `artifact-read`), the error class, the
chunk index and offset, the bytes the guest acknowledged, QGA's own error class
and text when it replied with an error, and whether the handle closed. A failing
close never hides the error that came before it. `push-failure.json`, beside the
receipt on the host, adds the wire bytes of the failing call and of its close.
They are written as ASCII, with a raw non-ASCII byte as `\xNN` and a backslash
doubled, so a raw 0xFF and QGA's escaped `�` look different. Past the
receipt's bound, only the call and the two classes stay in the receipt.

The job's own code is cached the same way. `render_job_body` is the host job with
the canonical definitions and the frozen bundle: the same bytes for every row of
one bundle, about 1.2 MB, kept beside the program record as `job-body.py`. The
submitted program is `render_loader`'s: the row's own `SPEC`, `SETUP`, `CONTEXT`
and `PLAN`, deflated, the body's digest and size, and a loader that opens the
cached body without following links, requires it owned by the account, private,
of that size and digest, and only then runs it. A body that is missing, changed
or open to others ends the job with exit 2 and `host_setup:job_body_unavailable`,
`host_setup:job_body_changed` or `host_setup:job_body_unsafe` before any guest
effect. Run that way it executes exactly what `render_program`'s single program
executes, which a test holds without a VM; the body binds none of the loader's
names. The submit is about 14 kB, so it goes in one inline SSH child instead of
the saved-program route the 1.2 MB program needed on every row.

The first contact of a submit is one read: the target's identity, exactly as
`_TARGET` prints it, and the cache state of every copy the row needs (the body
and its packages), checked as staging checks a copy. Only an absent copy is
written; a copy that differs, or a cache folder others can open, refuses before
any preparation. One transport admission covers every call of a submit and is the
sum of their budgets: 1,320 s for the body and none, 2,220 s with one package.
Only the durable submit command can start the job. The target read, the staging
and the carrier's preparation create no job and touch no guest. So a submit that
fails before that command is sent, a lost reply included, ends as
`not_submitted` with the reason `not_submitted:<refusal>`. That state is final.
Status, resume and collect return it without a host read, a repeat start returns
it as a duplicate, and a new attempt needs a new correlation. A failure at or
after the submit command ends the start as `submit_response_unavailable`. Status
and resume then only look for the job by correlation, and nothing submits it
again. The Windows matrix classifies a `not_submitted` row as `refused`, so it
makes no claim.

The direct script holds one readiness admission for a whole row with
`driver.row_admission(plan)`: submit, waits, status and collect then enter no
admission of their own, and every SSH child still revalidates the admitted
transport at its dispatch (connection, boot and account), as each call's own
admission did. A call that got no reply, or whose readiness was refused, leaves
the admission stale, and the next call admits afresh before it sends anything.
The MCP route's dispatch boundary admits each of its calls as before.

`driver.wait_job(plan, seconds)` is one host read of at most 110 s over the
durable owner's own job directory, polled every half second: it returns when the
owner's terminal record exists or the owner it recorded is gone. It reads host
files only (no lock, QMP, QGA or guest) and decides nothing: its caller asks
status then, and status reads the original job as always. A failed read returns
none and proves nothing. The direct script waits this way instead of sleeping and
asking status, and still asks status at least every 10 minutes.

Each driver call and admission appends a line to `timing.jsonl` beside the
program record (phase, start, seconds, return code, argv and reply bytes), and the
job writes `timing.json` beside its receipt (each stage's and guest program's
seconds), which collect keeps as `host-timing.json`. Neither is evidence or part
of the collection, and a line that cannot be written is simply missing.

A product row may run after passed rows without a reset in between. The direct
script then constructs the driver with `clean_start=True`, which puts
`cleanStart` into the plan of a product row (never a setup row, a postboot or the
MCP route). The job counts the jobs on this VM whose `job-exit.json` is not older
than the prior install's. With none, the row runs exactly as right after its
reset and records nothing new. Otherwise it refuses with
`clean_start_unclean_job` before any guest contact unless each of them passed or
was refused; then, after its context, it runs a read-only SYSTEM census: no
process of the product, its helpers or the bundled runtime, none running from
the install or Python folder, and no `VpnControlOrdinary-*` task. Anything found
is the known failure `clean_start_drift:process:<image>` or `clean_start_drift:task`
before any publish, and the receipt records `cleanStart` (jobs since the install,
processes and tasks found). The publish stage then checks the registration and
the complete installed tree against the install as always. Its caller resets and
runs the row again as a new operation.

A product row pushes no MSI. Before its fence the job reads the named install's
receipt on the host and exits 2 unless that job passed on this VM with the same
package digest and product version (`prior_install_unavailable`,
`prior_install_other_package`). In the guest it then requires exactly one per-user
registration with that product code and version, installed in the install folder
(`installed_registration_differs`), and a complete installed-tree digest and file
count equal to the recorded ones (`installed_tree_differs`). The installed
application is pinned only in the worker request, so an MSI may replace its files.
The Python and installed trees are listed first and counted with the request's
fixed pins, a document row's guest-made document among them: above 4,096 file or
1,024 directory pins the row ends with the known failure `worker_pin_bound`,
before any tree pin and before any task.

`windows-python-install` refuses when the Python tree already exists
(`python_tree_present`). `windows-msi-base-install` refuses when any vpn-control
product is registered (`installed_product_state`) or when the install folder,
`%LOCALAPPDATA%\vpn-control`, already holds a file (`installed_files_present`;
empty folders do not count, as the tree digest counts only files).
`windows-msi-base-reset` is the VM's way back to a clean base: it needs exactly one
per-user registration, removes it with `msiexec /x` and the exact product code the
guest reported, then installs the admitted base as the install row does. Its
worker request also names `uninstallRoot`, the install folder, which the planner
requires inside LocalAppData, not LocalAppData itself, and apart from the
operation root. A failed removal installs nothing. If the removal left any file
there, the worker writes the event `uninstall-left-files` and exits 1 without
installing, and the receipt shows only `task_exit_code`. The VM then has no
product but files in that folder, so a base install refuses until someone clears
it; no tool route does.

The registration read runs as SYSTEM and enumerates every user and context at once
(`S-1-1-0`, context 7), keeping the ordinary user's rows and the machine's and
naming products by `InstalledProductName`, as the natively proven installed-context
reader does. A name it cannot read is counted, never dropped silently. Each row's
package code is the revision number of the cached package that the installed
property `LocalPackage` names, because SYSTEM's `MsiGetProductInfoExW` answers 1608
for `PackageCode` of a per-user install. A failed receipt check names that check
after a colon, as a finite code and never as guest text: for example
`publisher_msi_receipt:package_shape_list`,
`installed_product_state:count_0:considered_12:unnamed_0` or
`installed_registration_differs:location`. A publisher program that fails names the
template's own code when its stderr carries one, for example
`publisher_refused:after-registration:PUB_MSI_INFO:LocalPackage:1608`.

A product row is `productAction` true and is `installed-package` evidence only
when the job is terminal, its collection complete, `windows.installedPackage` true
and `packageSha256` equal to the `targetPackage` ID. The receipt sets
`installedPackage` only for a passed product row whose registration and installed
tree matched and whose task passed its check. A stopped product row never claims
it: a job stopped early by `stop_after`, which only the direct script sets,
records `installedPackage` false and its `stoppedAfter`, and `public_evidence`
reads it as `installed-package-unproven` whatever else its receipt says.

Reboot rows come in pairs around `readiness-reboot`, which stays the only reboot
submitter: `windows-reboot-reconnect.pre|.post`, `windows-reboot-explicit-off.pre|.post`
and `windows-autostart-migration.pre|.post`. Each `.pre` runs the
`windows-preboot-reboot` worker action in a fresh product workspace: an in-guest
SOCKS upstream on loopback port 41081, the owned profile (source set before the
first location), autostart migration from a legacy HighestAvailable task to the
public LeastPrivilege one, then a graceful quit of its own serve. The legacy task is
planted by the SYSTEM run before it starts the ordinary owner, for the ordinary user,
from the pinned `windows_autostart_create_highest_fixture.ps1`: the pre-migration
product registered it from an elevated process, and an unelevated ordinary token may
not. So the owner's first observation is that task, and no public toggle comes before
it. A planting that fails is `refused_before_launch` and leaves nothing. A planted task
that the product never migrated is removed in the run's closing. It then starts
the app through the product's own autostart task, measures traffic for reconnect,
stops its upstream and finishes with the app running and no child of its own. A
passed `.pre` publishes `product-allowance.json` into its own ProgramData workspace
through the SYSTEM publisher (stage `declare`); its receipt's `preboot` part names
the workspace, the checkpoint event and the boot time. The package has no loose
runtime: it ships inside an app jar and is extracted per workspace, so every reboot
row takes the runtime digest from `runtimeAuthority` in the installed
`app\native\windows-amd64\native-helpers.json`. The job reads that file's bytes
once over the agent against its installed-tree pin; the guest action reads the same
held file. A missing or malformed record is the known failure
`installed_runtime_authority` at publish.

Each `.post` is a new operation whose `scenarioInput` names its `.pre` in
`priorPreboot` (only `.post` inputs carry that field). It refuses with exit 2 and no
guest program unless that `.pre` passed on the same install record and package
(`prior_preboot_other_install` otherwise), and unless exactly one
`readiness-recovery-<id>` reboot journal in the VM root was submitted from the
`.pre`'s boot with an idle census that knew every declared product process
(`prior_preboot_reboot_unproven` otherwise: a crash or a restart is no reboot of the
pair). It then refuses after its read-only context unless the guest's boot FILETIME
is later than the `.pre`'s (`preboot_boot_not_newer`): the kernel boot identifier is
the same on every boot of a clone. Its receipt's `reboot.readinessReboot` names that
journal's recovery and operation IDs. It runs `windows-postboot-final` on the same
workspace: the startup census before any query, the task ran this boot, the GUI and
controller are the launcher-plus-JVM tree under the ordinary token, reconnect or off
held, GUI show and hide, traffic for reconnect, then autostart off and quit.
`windows-query-owner-gui-reconnect` is rebootless: `status` with no owner never
starts one, so a config query (`locations list`) starts a transient owner that never
connects, then a GUI restores the remembered intent once. All of these are product
rows that name their `priorInstall` and `targetPackage`.

One reboot chain runs at a time on a machine. Every reboot row's receipt has a
`reboot` part; for a `.pre` its `autostart` is `changed` when the owner's journal
holds an autostart or product-start intent, `untouched` when the owner never ran or
never got that far, and `unknown` when its evidence could not be read. A `.pre` that
is not `untouched` holds the machine until a passed `.post` names it: meanwhile
every other reboot row is refused with `reboot_chain_open`, and a `.post` for a
closed `.pre` with `prior_preboot_unavailable`. A prior job of the machine without a
readable receipt refuses every reboot row with `reboot_chain_unknown`. A failed `.pre`
that changed autostart may have left the legacy task or the app behind, so nothing
closes it on that clone; a new attempt is a new operation on another clone. A known refusal in
either action retires what the owner still runs: the owned upstream, then the
`.pre`'s own serve or the query GUI through the same journaled public quit to its
controller. The owner then finishes with exit 1; only an effect whose outcome was not
observed parks.

The order on one VM: package and install setup, then `.pre`, collect,
`readiness-reboot`, `readiness-ensure` (the sign-in fires the logon trigger), then
`.post`. The idle census lets the reboot through with the app running only for a

  folder before the census. An expired prompt is the grant's own known `CANCELLED`.

The product writes the journal into its state folder before UAC and before every native input
of a mutable job (`DesktopWindowsVpnBroker.prepareCaptured`). While resources-grant and
stage-squat wait for it (at most 120 s), they read their own operation every 5 s with
`operations status`; that read is never a resend. The wait can end three ways:

- A definite refusal (an exit-1 code or `CANCELLED`, the stages' `REFUSED_EXITS`) with still no
  journal means the request ended before any prompt. The stages then check that A and pending B
  are as before, the census shows no broker, stage, route or new runtime, and there is still no
  journal. With all of that true the row closes as a known failure
  (`scoped-tun-reserved-ended-before-journal`, with the product's terminal in the event).
  Otherwise the owner parks.
- `OK` with no journal, or a code the product classes as leaving the outcome open (`TIMEOUT`,
  `OUTCOME_UNKNOWN`, `UNAVAILABLE`, `INCOMPATIBLE_PROTOCOL`), parks with
  `scoped-tun-reserved-ended-outcome-open-no-replay`.
- An operation still pending at the bound parks with `scoped-tun-reserved-journal-absent-no-replay`.

Every one of these ends first writes a `scoped-tun-reserved-journal-wait` event with the last
status it read.

The case settles the run (`settle_counterfeit`):

- Passed: the answer is one of the refusals; the root and canary are unchanged in
  SYSTEM's view and in the case's own, the root holding the canary alone; owner,
  configuration and disconnected runtime are the same; the base registration and every
  pinned base file are in place; then the serve has quit, the fixture is closed and the

- Failed (known): any other definite answer, an expired prompt's CANCELLED among them,

then needs, for a pass, the root listed as SYSTEM at `terminal-actors` to hold the

result of 0 can release. Run it on a clone where no grant ever ran, or before any

direct run (`TEST-002`). The set's route shapes are its rows' static shapes (`route_shapes`: `plain`, `uac-approve`,
`uac-deny`, `update`, `reboot-pre`, `reboot-post`; QRY's rebootless phase is `plain`) plus `longest`, the counted row
whose direct pass made the most job polls (then the longest deadline, then the name), and `largest-evidence`, the
counted row whose direct pass collected the most bytes. Each static shape needs a passed MCP run of some named row
with it; `longest` and `largest-evidence` need their own row's. While a shape has no such twin, every row with it is
a representative and needs its own. `mcp_admission(root, correlationId)`, or
`python3 -m agent_tools.native_scenario_windows mcp-admission <correlationId>...`, is the read-only dry run of an
MCP start of that journaled operation now: it compiles `resolve_bundle` and `resolve_input` from `mcp_server.py`'s
scenario actions, so no copy can drift, verifies registry bytes without housekeeping, and checks `artifact-keys`
(the adapter's `SCENARIO_ARTIFACT_KEYS`), `bundle-single-location` (the manifest at one local location; two copies
refused the MCP twin `055c3b3c`), `input-at-collect` (the input resolves as collect resolves it),
`admission-gates` (`native_scenario_ssh.admit_start` with the route's resolver) and `repeat-start` (a repeat of the
operation reaches the executor's duplicate answer, which a bundle changed in the checkout refused for `3a1459ee`). A
follow that ends before terminal is no admission fact; the longest row's real twin carries it. The review's `mcpRoute`
names the required, covered and uncovered shapes, the longest and largest rows, the representatives and each dry run,
and the evidence document keeps it with each row's `polls` and `collectedBytes`. `matrix-record` re-derives the rule
from that document (`verify_route_document`) and refuses a passed record of a Windows requirement the driver maps
unless it comes from this evidence. The observation reads each journal without collecting, so call
`scenario-status` for every row first, then it classifies each row:

- `passed`: terminal, collection complete, unstopped, and installed-package by the
  rule above; a grant row also with its approval proven (the update rows above).
- `approval-unproven`: a grant run whose package is proven but whose receipt does
  not prove its approving account, the coordinator elevated under it and the worker
  as the original user.
- `approval-unanswered`: a TUN grant (`approveJoin`) whose prompt expired into the
  product's `cancelled` known end because its `windows-uac-decision` refused before
  any input. Collect reads that from the decision's host folder (`_READ_DECISION`:
  no input journal, every attempt terminal `input-refused` with nothing attempted,
  none refused for a prompt another decision burned or whose input stays unknown) and
  names it `approve-refused:<reason>` in `uacDecision`. Nothing approved the broker,
  so the run says nothing of the product.
- `installed-package-unproven`, `approval-unproven`, `approval-unanswered`, `stopped`, `refused` (exit 2, no receipt), `setup`,
  `failed-before-task` (a known failure before the owner's task ran) and
  `failed-after-task` never count. `failed-after-task` is a known failure of the
  harness once the task finished: the task journal (`task_events`), the command line
  read (`task_command_line`), the evidence copy after a passed task (`evidence_*`),
  a preboot declaration, a task exit other than the owner's own 1, or a LOCAL SERVICE
  probe the harness did not complete (`document_principal_unserved`, `_refused`,
  `_window_closed`, `_result_missing`, `_result_left`).
- `failed`: the owner's own failure, `task_exit_code` with owner and terminal exit
  code 1, which a case oracle failure ends with; recorded at once. The receipt cannot
  tell a case oracle from the owner's own precondition, so review the events first.
- `failed-harness` (`TEST-008`): the same exit 1 when the run's pulled evidence copy,
  the one its receipt hashed, holds exactly one `known-failure-closing` and one
  `known-failure-closed` record with the same reason and an `owner-terminal` of exit 1,
  and that reason is on the reviewed list `MATRIX_HARNESS_FAILURES`: a harness fixture
  the OS refused before the product took part (`document-<race|persistence|export|spool>-fixture-refused:<step>:<code>`,
  as DOC `83484649` closed with `document-race-fixture-refused:rename-away:32`) or a
  work or cache fixture not ready before the serve existed
  (`document-<work|cache>-fixture-not-ready:<timeout|ended|refused>:...`). The review
  names it in `harnessFailure`. It never counts and is never recorded: while one is
  named, its scenarios are `failed-harness` (a failed or unknown run of the scenario
  still wins) and the observation refuses as `windows_matrix_harness_failure:<scenario>`,
  so fix the tool and rerun the row, then name only the rerun. It does not hold a later
  pass of the package (`windows_matrix_unrecorded_outcome` skips it). Any other reason,
  a missing or changed copy, or a second closing stays `failed`.
- `suspect`: a pass that the next row's clean start found state left behind by
  (`native_row_queue.mark_suspect`; an unreadable mark is suspect too). It never
  counts, is never measured for the MCP route, and does not hold a later pass;
  rerun the row after a reset. Beside a `failed-harness` run of the same requirement
  each keeps its own rule
  (`test_native_scenario_windows_matrix.HarnessBesideSuspectTests`).
- `failed-principal`: a DOC run whose owner passed (owner and terminal exit code 0)
  and whose LOCAL SERVICE probe then proved no denial of the owner-private endpoint
  (`document_principal_not_denied`): the product's verdict, recorded at once. It fails
  `wrong-principal-owner-context-kind` alone (`MATRIX_PRINCIPAL`); for DOC's other
  scenarios that run never counts. The receipt cannot tell an endpoint the probe
  opened from a probe that ran under another identity or met another error, so review
  the job's `principal-probe.json` first.
- `unknown`: the job's own UNKNOWN exit (`job_exit_unknown:*`), the durable job's
  final UNKNOWNs (`original_owner_missing`, `boot_changed` after a host reboot,
  `output_overflow`) or a collection over its bound, recorded at once.

Anything else, a running job, another unknown reason such as a missed read, or a
terminal job not yet collected, refuses the whole observation as
`windows_matrix_row_unsettled`. Every product row must name one source, version,
frozen set and target package (`windows_matrix_mixed_source`,
`windows_matrix_mixed_package`). A failed or unknown row yields a `failed` or
`unknown` observation of its own scenarios (a `failed-principal` run, of
`wrong-principal-owner-context-kind` alone), the rest listed in `missingEvidence`, with
`inspect-evidence` next. A `passed` observation needs every applicable scenario passed
(`windows_matrix_incomplete:<open>` otherwise), is refused while an unretracted passed
record of that requirement and source exists, and is refused as
`windows_matrix_unrecorded_outcome:<correlationId>` while any settled `failed` or
`unknown` run of a counted row on that target package (for
`document-persistence-transfer` also a `failed-principal` one), named or not, is missing from
every recorded observation of the requirement and source. So a failure or an unknown
is recorded before the pass, which then stands beside it as `conflicting` until a
reviewer retracts one with a reason. A run still unsettled has no outcome yet and does
not hold the pass. `document-persistence-transfer` is `limited`, with
`android-48m-heap` missing. The evidence is create-only at
`.rag_index/native-acceptance-evidence/<requirement>-<sha12>.json`, published as the
ledger publishes a receipt (a synced temporary file linked under its name, so an
interrupted write leaves nothing there): each row's classification, route, receipt
SHA-256 and failure token, and each scenario's state. `immutableArtifactIDs` are the
target package and any fixture receipt of the counted rows, verified read-only for
the platform and the package source; `environment` is `windows-qemu-<deployment>`, or
`windows-qemu-<n>-clones-<digest>` for several clones. For review,
`python3 -m agent_tools.native_scenario_windows matrix-observation --requirement <id>
--reviewer-attestation "<text>" <correlationId>...` prints the observation on stdout
and the row review on stderr, or exits 1 with a finite refusal, including
`windows_matrix_ledger_unavailable` for a ledger it cannot read and
`windows_matrix_evidence_unavailable` for evidence it cannot write; record by passing
the printed object to `matrix-record`. Today no Windows requirement can pass.
`windows-installer-lifecycle` maps all eight scenarios, but only to update and reboot
rows. `different-admin` and `protected-storage-rejected` are still refused at
admission, so `different-approving-admin`, `original-user-worker` and
`protected-storage-adversarial` cannot pass. Neither can `msi-installer`, whose
`native-install-failed` is refused too. The other Windows requirements each have an
unmapped scenario.

`matrix-status` counts a record only when its `originalSourceSHA`, the package's
source commit, is the checked-out HEAD, or through an equivalence link to HEAD. A link
exists only for a complete passed full-native record, never for a limited, failed or
unknown one, and not while any other record of that requirement and source is
partial, failed or unknown, retracted or not. Between the source and HEAD no input a
scenario executed may change, with no rename, mode change or symlink anywhere in the
diff. `native_artifact_reuse._ScopedInputs` derives those inputs from each commit's own
files: the product build inputs (every tracked path outside `agent_tools/`, documentation
and tests, so product code, `settings.gradle.kts` and build files, `scripts/` other than
`test_*.py`, `.github/` and `gradle.properties`), the files the `_SCENARIOS` table of
`native_scenario_bundle.py` ships to a guest, and the executed-input closure of every
`agent_tools` module that imports the bundle, execution, matrix or equivalence module:
their imports, the modules they load by name (the MCP server's `_VM_NATIVE_ADAPTERS`,
`_agent_module` and `import_module` strings, source-session loads), sibling sources named
by `with_name` (the selector `affected_agent_tests.py`), and the non-Python files those
modules name, including a module's own `with_suffix` resource (such as
`native_acceptance_requirements.json`, `tool_action_policy.json` and the dispatch
catalog `readiness_vm_dispatch.json`). A path is executed when either commit executes
it, and the executed paths of both commits must be byte-identical. Not executed, and so kept:
`docs/`, `agent_docs/` and Markdown outside the Gradle projects; Gradle test source sets
(`src/test`, `src/*Test`) and directories only they add (`visual-tests/`); `tests/`,
`scripts/**/test_*.py` outside the bundle, `agent_tools/tests/` and its fixtures; the
selector's own metadata (the files `affected_agent_tests.py` names, such as
`affected_agent_test_dependencies.json`, even where `mcp_server.py` reads them to load
the selector); and any other `agent_tools` file outside the closure. When only such
paths changed, from a clean checkout at HEAD call
`vm_workflow matrix-equivalence-record` with the receipt ID, the target package's
frozen `artifactSetId`, `targetSourceSHA` HEAD and an attestation, once per record and
HEAD, then finish its `requiredCurrentChecks`: exact-SHA CI for HEAD, and the changed
tool tests when tests, fixtures, metadata or tools changed. Any other change needs a new
package built from a commit after it, a new frozen set and base install, and the sweep
again; the old records stay historical. A failed or unknown record, retracted or not,
blocks every later link of its requirement and source, which is why `failed` is only the
owner's own exit 1 and a harness failure is never recorded.

Before a final sweep, `sweep_eligibility(root, artifactSetId, requirementIds)`, or
`python3 -m agent_tools.native_scenario_windows sweep-eligibility --artifact-set <id>
[--requirement <id>]...`, classifies read-only whether a pass of each planned row on that
frozen set would count at the checkout's HEAD, and exits 1 with
`windows_sweep_cannot_count:<first refusal>` when it would not; a refused sweep does not
start (`TEST-007`). It refuses an unverified set or one without a Windows
`desktop-package`, a set whose source neither is HEAD nor reaches it by an equivalence
proof, a limited requirement whose source is not HEAD itself (GAP-DOC), a requirement
with an unmapped scenario (`windows-visual` has no matrix producer), an unretracted pass
or any failed or unknown record of the requirement and source, a settled failed or
unknown run of a counted row on the target package that no observation records, a
refused row, and an update row whose set lacks its fixture receipt or fault artifacts.
With no requirement named it checks every requirement the driver maps. `mcpTwins` names
one row per static shape; the longest and largest-evidence rows are decided by the direct
passes.

#### Windows UAC decision

`vm_workflow windows-uac-decision` takes exactly `host`, `environment`,
`correlationId`, `prompt` (`install-helper` or `vpn-broker`) and `decision`
(`approve` or `deny`). It answers the one prompt of a running scenario whose
dotted name is in the closed table of `agent_tools/windows_uac_decision.py`, and
only when that row's prompt and decision equal the inputs. A row whose owner
published its prompt event reports `uac-pending:<prompt>:<decision>` in
`scenario-status`; a fixed client polls for it, because a model turn may not fit
the prompt's lifetime, and waits for it on the host with the driver's
`wait_uac_pending` rather than sleeping between status calls. The job and the owner never call or wait on this action.
The token outlives the prompt, so the client may call on every poll: a refusal
that proved only "not yet" (event not pending, a failed guest read, a busy lock,
nothing sent) permits another submit; any other refusal, such as no prompt
within the 30 s gate, leaves the prompt to expire, and a repeat returns that
refusal with no packet. A deny row is admitted at `scenario-start` only where
collect joins the decision's input terminal, because an expired prompt ends as the
same public `CANCELLED` as Esc. `windows-scoped-tun.restart-deny` and
`windows-public-update.uac-denied` are the deny rows admitted today.

Proof comes before any key: reviewed pixel crops of a QMP frame and a SYSTEM
census of `consent.exe` (one, System32, signed by Microsoft Windows, parent
Appinfo, younger than 90 s), the owner's pending event and the UAC policy. The
secure desktop draws the same prompt at another height on another clone or run
(S_D4: NG's review frame 63 rows below ND's, every reviewed pixel the same), so
the gate searches the vertical offset only (`_uac_locate`): within the frame,
every crop must match its reviewed bytes exactly at one and the same offset, two
such offsets refuse `instance_uac_frame_ambiguous`, and the field is read at that
offset. x, size and bytes stay the review's. The 90 s rule holds at the burn,
counting frames read after the census, and a dark field is read again within the
gate, since the caret blinks there. The decision's one journaled pointer move,
shared with its review, parks the arrow in the top right corner (an absolute
mouse jumps there, a relative one takes 16 steps toward it), which no searched
offset of the dialog reaches; it is made for a black display, which it wakes,
and for the first lit frame that is not the prompt, since an arrow left over a
crop would hide the prompt for the whole gate. Never a second move, never a
button. A refusal at the bound (`instance_uac_frame_unrecognized`,
`instance_uac_field_not_empty` or `instance_uac_frame_ambiguous`) also says what
its last frame showed, in a `frame` field of the refusal and its journaled
result: `offsetY`, the offset nearest the review at which most crops matched,
`cropsMatched` there, per reviewed crop in the profile's order (the `account`
crop last), and `fieldDarkPixels` there. Every crop false is a screen without
the reviewed prompt, such as one waiting as a taskbar button; one false crop is
something over that region or a per-clone difference. The refusal also publishes
that frame beside its terminal in the VM root, the reply carries its exact bytes,
and the client keeps them as `attempt-NNNN.frame.ppm` and `.frame.png` in the
local decision journal, named by `framePath` and `pngPath`; a frame that cannot
be kept as named leaves the refusal without it. The facts and the frame never
admit anything: the gate still needs every crop. Deny is
one Esc and opens no credential. Approve reads the approving account's secret through
`SecretFile` and passes it on SSH stdin to a detached child: `final-administrator.secret`,
or for the one row of the closed table `APPROVERS`, `different-admin`, the clone's
`second-administrator.secret`. The census then expects that account's SID, read by
its name in the setup, in the pending event, and a clone without the account
refuses the row before contact (`uac_second_administrator_absent`). A create-only burn per
prompt and the input journal precede the first key, so a lost reply never types
twice; a repeat is a status packet with no key path. The reply is an
acknowledgement only: `approvalSucceeded` and `productOutcomeProved` are always
false, and the scenario's own collection proves the product outcome. Profiles are
private, under `.runtime/windows-uac-profiles/<deployment>/<prompt>.json`, made by
`reviewed_uac_profile` from a frame the reviewer opened. The second administrator's
is `install-helper.second-administrator.json`. On a clone with two administrators a
credential prompt offers both, so every approve profile there also names its
`approver` and an `account` crop, the account name the prompt shows selected, with
at most seven other crops: the decision types a secret only into a frame that shows
its own account selected, and refuses `uac_profile_unreviewed` for a profile
without one. Guest files stay under the
VM-root subdirectory `windows-uac/`, published whole, and the fence is a flat
`direct-guest-*` journal, so `readiness-reboot` refuses while input is open and
sign-in history never sees them. A known input closes the fence, and status
closes it if that close was lost. An input whose owner died stays UNKNOWN:
status records `input-outcome-unknown` once the prompt is gone but never closes
the fence, so reboots and new jobs on that clone refuse until the original is
read. No sign-in source pin moves, and the module is not alias-pinned.

`vm_workflow windows-uac-review` is the sibling closed action that gives a clone
its first reviewed frame. It takes the same five fields, route, transport
admission and closure, and needs no profile. It runs the decision's admission:
the scenario journal and that row's pending event, the SYSTEM census of
`consent.exe` and the UAC policy. A black frame gets the decision's own single
journaled pointer move, the park in the top right corner: the journal is the decision's `pointer.intent.json`, so a
review and the decision of one scenario move the pointer once between them, and
a later packet that still sees black refuses `instance_uac_display_black` instead
of moving again. Frames are then read for up to 10 s until the display shows
something, the frame read a second later is kept, the same consent process is
checked again, and the review stops. It writes no burn, input journal, fence or
decision terminal, opens no credential, sends no key or click and reads no
stdin. A prompt its decision burned or began to answer is refused. The reply
names `pointerMoved` and `wakeMilliseconds`, the time from that attempt's move to
the first lit frame in half-second reads. The decision gives its own move one
second: on a clone that needs longer, review the prompt first in the run that
answers it, and the decision then finds the display lit. Its reply is
`review-frame-retained`, class
`uac-review-frame`, never an answer: the prompt and the status token stay open,
and a decision may follow within its gate. Its journal is
`.runtime/windows-uac-reviews/<reviewId>/` beside the decision's, with the frame as
`frame.ppm` and a lossless `frame.png` for viewing. A kept frame is returned again
with no packet, a lost reply is only read by a status packet, and as for the
decision only a "not yet" refusal permits another submit. For a review
`instance_uac_display_black` is one as well: the pointer journal forbids a second
move, so the next review only reads the census and frames, and a slow wake costs
a call, not the run. The decision keeps its own rule, and black ends its submits.

Both UAC actions answer what local files decide (the journal, the table, the
binding, the profile and retained results) before the transport admission, so
such a refusal never waits on SSH; the admitted call runs every gate again. The
binding is read without the sign-in stack, the scenario driver loads at the first
contact, and the server compiles its own source once per process instead of once
per adapter load. Each of those checks is unchanged. A one-shot CLI command no
longer imports the MCP package: the server imports it for `serve` and for
importers only, and `mcp_tool.sh` imports it in its probe for `serve` only, while
a one-shot command still imports `cryptography` and still requires the MCP
package to be installed. A client that polls for a prompt should call the server
through that launcher or directly, once per poll.

The 90 s rule counts from the prompt's birth, so everything between the prompt and
the census spends it. Runs `d476687a` and `a47da155` (clone `192e5a3d`,
`windows-scoped-tun.restart-deny`) refused `instance_uac_prompt_age` on their first
review: a client that slept 5 s and then asked status saw the token one status round
trip late (39 to 56 s each), and the call itself then took about 95 s and 80 s to its
census. Three changes hold that down without moving the rule. Every UAC packet
(decide, status, review, review status and the visual route's) is deflated into an
inline carrier of about 24 to 33 kB, under `INLINE_CARRIER_BYTES` (48 000), so
`ssh_transport` sends it in one SSH child instead of staging the 86 to 94 kB source
over a second connection with its custody checks. The scenario driver keeps the
job's context (`uac-context.json`, written once by the job's context stage) as first
read, create-only under `.rag_index/native-scenario-windows/<correlation>/`, and the
action reads that copy, checked as a read one is, with no SSH and no driver import;
without it the action reads once as before and the driver keeps it. The packet still
checks the context against the live guest. A client waits for the token with the
driver's `wait_uac_pending(plan, seconds)`: one host read of at most 60 s that polls
the job's status copy every quarter second, beside the job and with no lock, QMP,
QGA or guest, returns when the row's event is pending with no decision terminal or
when the job has its receipt, and keeps the context. Each attempt that sent a packet
keeps `attempt-NNNN.timing.json` beside its journal: its wall start, where the context
came from, and seconds to the gates, the context, the send and the reply.

A profile for a clone, by one operator, with no other guest action in between:

1. Start a run of a row whose prompt the profile is for (`vpn-broker` from
   `windows-scoped-tun.restart-deny`, `install-helper` from an update row), on
   the discovery package, and poll until `uac-pending:<prompt>:<decision>`.
2. Call `windows-uac-review` with that run's five fields. Call again on a later
   poll only after a "not yet" refusal or `instance_uac_display_black`; the prompt
   then expires unanswered.
3. Open `pngPath` and check it: the prompt up and the password box empty. After a
   move the arrow is in the top right corner (frames reviewed before the park
   moved show it at the centre).
4. Choose one to eight crops of fixed dialog pixels and the field, the part of the
   password box where characters appear. None may meet the old parking place
   `[w/2-4, h/2-4, w/2+24, h/2+40]` or the 32 rightmost columns, no crop may meet
   the field, and a crop holds no pointer. Choose text, not plain fill: the
   review refuses `windows_uac_profile_ambiguous` unless the crops show the prompt
   at one vertical offset only. `max_dark_pixels` admits the caret if the frame
   shows it. The computer name is per clone: each clone needs its own profile.
5. `frame, record = retained_review_frame(root, correlationId)`, then
   `reviewed_uac_profile(root, record["environment"], record["prompt"], frame,
   crops, field, max_dark_pixels)` writes the create-only profile under
   `.runtime/windows-uac-profiles/`. On a clone with a second administrator, add
   `approver` and `account`, the region of the selected account's name, after
   checking the frame shows that account selected: `approver="second-administrator"`
   from a `different-admin` run, `approver="administrator"` from any other approve
   row. A frame that shows the other account selected makes no profile: the
   decision types only into the account the prompt offers first.
6. Answer the prompt of a later run with `windows-uac-decision`.

The decision and the review need a running scenario of the ordinary user. A
`windowsUacVisual` clone has none: its console is its filtered administrator, and
it runs no scenario job. `windows-uac-qualification.<answer>` therefore stays a
direct table rung with no scenario row. A row would need the scenario bundle, the
ordinary root and a producer no file has, and its prompt would not stand in for a
product prompt's profile.

##### Windows UAC visual prompt

`vm_workflow windows-uac-visual` is the closed route for the `windows-uac` scene
on such a clone (`agent_tools/windows_uac_visual.py`). It takes exactly
`deploymentId`, `operationId` (a new UUID per prompt) and `step` (`raise` or
`cancel`). The host comes from the deployment's own start intent, which must be a
`windowsUacVisual`, `en-US` one. It is setup class, `uac-visual-setup`: never
product evidence, never an approval, with no credential and no profile.

`raise` reads `visual-session-qualified.json`, which that deployment's qualification
left in its VM root, and proves in a SYSTEM census that the console is still that
session: the administrator's SID, the same explorer by pid and birth, the boot, the
UAC policy, the administrator's `en-US` layout, an unlocked session, no prompt and
no shell on that desktop. It then opens its fence and parks the pointer once, with
no button: an absolute device jumps to the top right corner, a relative one gets a
bounded run of steps towards it. The park wakes a sleeping display and keeps the
arrow out of the scene. Frames are read until the display shows something. Then
come `Esc`, `Esc` and `Win+R`, and the frame must change in the Run dialog's corner
and almost nowhere else; otherwise one `Esc` closes whatever opened and nothing is
typed. The command is the visual driver's own, `powershell start powershell -verb
runas`. The prompt is proven twice: one signed `consent.exe` of that session under
Appinfo with exactly one requesting shell, and a frame that changed in at least
half its pixels, because the secure desktop dims the whole screen while a prompt
waiting as a taskbar button does not. `raise` stops there with the prompt open.

`cancel` sends one `Esc`, burned before it is sent, and only to the prompt that
`raise` proved shown, while that same consent process is younger than 90 s. An
older one is left to expire, which is the same denial, and a prompt the operation
never recorded is waited out and never keyed. It then proves the prompt gone and
no shell left on that desktop, which an approval would have left, closes the
fence and names the frame operations whose result was written while that prompt
was still up. A prompt still up after two exit reads is reported
`visual-prompt-open`, and the next call goes on. Every repeat of a step is a settle
packet that embeds no pointer, key or frame code: a raise is never typed twice and
the `Esc` is never sent twice. A raise that began and failed says `cancelRequired`.

The scene, by one operator, direct first (TEST-002):

1. The clone is started, qualified (`visualFilteredAdminReady`) and secured.
2. Direct: call `windows_uac_visual.prompt(root, {"deploymentId": <id>,
   "operationId": <new uuid>, "step": "raise"})` from a private helper, outside MCP.
3. At `visual-prompt-raised`, at once: `vm_workflow windows-vm-deploy-frame` with
   that `deploymentId` and a new frame `operationId`. Its journal is the folder of
   the reply's `framePath`.
4. Then the same call as step 2 with `"step": "cancel"`, repeated while it answers
   `visual-prompt-open`, until `visual-prompt-closed`. `framesDuringPrompt` should
   name the frame operation of step 3.
5. Open the frame: the consent prompt for Windows PowerShell, `No` focused, the
   whole screen dimmed, no arrow in the dialog.
6. MCP: repeat steps 2 to 4 through `vm_workflow windows-uac-visual` with a new
   `operationId` and a new frame operation, then collect that frame with
   `capture-local --target deployment:<id>` as
   [visual regression](../visual-regression.md) describes, and review it.
